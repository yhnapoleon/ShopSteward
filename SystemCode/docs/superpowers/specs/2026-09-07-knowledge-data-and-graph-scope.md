# K0前置决策：哪些数据进入知识检索，哪些关系适合知识图谱

> 2026-09-07执行更新：用户已授权K0–K1。本轮范围与选型以[K0–K1执行计划](../plans/2026-09-07-k0-k1-execution.md)为准。原OpenSearch+BGE-M3是候选基线；K1上传为201/UPLOADED/NOT_INDEXED，所有写入支持幂等与CAS（创建无需CAS），真实索引任务在K2接入。下文保留完整后续规划，不能把planned能力当已实现。

日期：2026-09-07。状态：**范围界定与实验设计，未实施知识图谱或K0运行实验**。

用户已授权先进行K0，并要求在开始前明确RAG数据范围及知识图谱的适用性。本文件回答该前置问题，补充[原设计](2026-09-07-knowledge-retrieval-design.md)与[实施计划](../plans/2026-09-07-knowledge-retrieval.md)。

## 1. 采用的范围判断

首版统一管理经营资料，支持元数据、关键词与混合检索；增加可追溯的文档—实体关联作为检索限定条件。K0比较SQL关联、混合检索和关系引导检索的效果。暂不把独立图数据库、全量自动实体关系抽取或Microsoft GraphRAG社区摘要系统作为前置依赖。

知识图谱可以加入，但需要回答“关联查找是否确有收益、哪些关系可靠、怎样维护”。结构明确并不自动意味着图谱更好；很多明确关联已能通过现有PG表的JOIN查询完成。

RAG是检索证据后生成回答的应用方式，并非一种只能存文本的数据库。图结构可以参与RAG的检索步骤；已有SQL事实、文档关键词和向量检索也可以作为并列工具。

## 2. 明确的数据分配表

| 数据 | 知识文档库/检索 | 向量化建议 | 图或实体关联 | 权威来源与边界 |
|---|---|---|---|---|
| 供应商交付说明、截单通知、缺货/停发通知 | **首批纳入**，保留版本、有效期、附件原文 | 自然语言条款采用BM25+向量；短通知先关键词 | 文档适用供应商/SKU、替代或补充的版本、明确涉及的订单 | 文档提供通知证据；实际订单状态仍查backend |
| 供应商合同、售后/退换/部分履约条款 | **首批纳入与备货直接相关的部分** | 条件、例外、跨章节解释适合混合检索 | 条款适用的供应商/商品/订单类型及明确例外 | 原文和条件同时返回；不能自动赋予Agent采购或法律判断权限 |
| 商品保质期、储存说明、包装规格、兼容/替代说明 | **首批纳入** | 长篇说明混合；简单规格精确查 | 类别、适用范围、经确认的有条件替代关系 | 参与数量换算/正式规划的字段需单独校验入业务表 |
| 收货检查、部分到货、缺货、临期处理SOP | **首批纳入** | 同义表达、异常处理适合混合检索 | SOP对应事件/角色/对象；必要时关联步骤 | 文档描述流程不等于运行时工作流；动作仍走既有业务用例 |
| 活动方案、备货要求、渠道安排 | **首批纳入** | 长文混合、日历精确 | 活动/现有Mission与涉及SKU、供应商文档 | 活动范围和需求数字如需算账，仍要进入正式业务输入 |
| 人工确认的经营复盘、供应商沟通纪要 | **首批纳入** | 相似情境与跨文档归纳适合混合检索 | 关联原Mission/Plan/Action、事件及支持段落 | 明确区分当时事实、作者判断和建议；总结不能产生新事实 |
| 当前价格、起订量、报价有效期、交期等正式输入 | 原文可作为上述资料保存 | 不靠向量查找当前精确数值 | Offer与供应商/SKU的关联可直接查询 | backend生效输入是权威；文档抽取只生成候选草稿 |
| 当前库存、现金、应收、在途、预留 | **不复制成RAG事实文本** | 不向量化 | 可沿现有实体关系定位，但不另存易过期金额 | 业务API/PG与确定性计算 |
| 订单、审批、采购、收货、销售、事件、流水 | 原始明细不整批转成文档语料；复盘可引用 | 不向量化全部流水 | 现有Mission→Plan→Action→Inbound等可用关系 | 现有业务表/API；需要统计则SQL聚合 |
| 用户USER/NOTES与活动SKILL | 不建设第二套活动记忆库 | 首版按scope直接加载 | 保持principal/store/task_type作用域 | 现有版本化知识服务，不由文档自动改写 |
| 外部通用经营文章、行业知识 | 后续精选，暂不作为首批主体 | 具体问题出现后决定 | 无明确消费者不建通用行业大图 | 来源、生效范围和适用性可核查；不替代本店事实 |
| 开发文档、测试报告、其他IH项目资料 | 默认不进店主知识库 | 不纳入本次经营语料 | 不混入经营实体图 | 开发资料与经营资料分别使用 |

“首批纳入”是K0语料范围，不表示系统已具备上传/管理接口。一个文件可同时包含结构化字段和叙述条款；不用在整份文件层面强迫选择SQL或RAG之一。

## 3. 结构、关系与规则要分别处理

| 特征 | 例子 | 最合适的起点 |
|---|---|---|
| 结构明确 | 按供应商+SKU查当前报价；按日期统计销售 | 数据库索引、JOIN、聚合 |
| 文章有章节层级 | 合同第3节交期，第3.2节节假日例外 | 文档结构、父段落还原与版本化定位 |
| 跨实体多步关系 | 供应商通知涉及哪些商品，这些商品关联哪些未结束Mission | 明确关系查询；关系路径较复杂时评估图遍历 |
| 条件/决策逻辑 | 可用现金不足则不能采购；未收到确认回执不能入账 | 确定性规则与状态机；图只链接对应规则说明和证据 |
| 因果判断 | 销量下降是不是供应商晚到造成的 | 时间证据、业务计算和专门分析；一条关联边不能证明因果 |

当前源码已有Store/Product/Offer/Stock、Mission/Plan/Action/Inbound等模型。Offer包含store/sku/supplier键，Mission与Action等也有业务关联。应先从这些对象读取，不能把已有关系重新交给LLM从文本猜一遍。

## 4. 知识图谱分三层考虑

### 4.1 第一层：业务关联和文档链接，值得直接规划

优先支持“这份资料适用于哪个供应商、商品、经营任务”和“这个实体有哪些有效资料”。它可以用PG外键、关联表和查询用例实现；关系可以画成图，但不因此需要独立图数据库。

最小对象集合：店铺、商品/SKU、供应商标识、报价、现有Mission、Plan、Action、文档版本、条款定位。供应商当前未必有独立主表；K0按Offer中的真实键识别，不能凭一个图节点宣布供应商主数据模块已完成。

关系类型按来源分开：

| 关系 | 来源 | 使用限制 |
|---|---|---|
| Store HAS_PRODUCT SKU | backend业务记录 | 使用店铺内规范ID，不能靠同名跨店合并 |
| Supplier HAS_OFFER Offer / Offer FOR_SKU SKU | backend报价对象 | “有报价”不等于长期供应承诺；保留报价版本/有效期 |
| Mission FOR_SKU SKU / Mission HAS_PLAN Plan / Plan HAS_ACTION Action | backend记录 | 通过现有ID查询；不得复制一套可修改业务状态 |
| DocumentVersion APPLIES_TO Entity | 人工录入标签或明确来源字段 | 控制检索适用范围；被“提到”不等于“适用于” |
| DocumentVersion HAS_SECTION Section | 解析器结构与定位 | 用于读取原文、还原上下文 |
| DocumentVersion SUPERSEDES DocumentVersion | 明确版本操作/文件声明并经确认 | 替换范围必须明确；普通通知不能自动覆盖整份合同 |
| Section MENTIONS Entity | 确定匹配或待确认抽取 | 只供发现资料；不能据此当作业务适用关系 |

### 4.2 第二层：跨文档关系引导检索，K0评估

适合的问题：

- “A供应商的停发通知可能涉及哪些SKU和进行中的经营任务？每个关联有什么依据？”
- “这个商品的替代候选有哪些，各自受哪些储存、包装或使用条件限制？”
- “这次部分到货应看哪份供应商条款和哪套店铺SOP？”
- “这条新通知修改了旧文件的哪一项要求，而不是整个旧文件？”

图先找实体路径与候选文档，再按版本/权限取原文片段；最终解释必须带完整证据。查询图后仍需要业务API和文档检索。

候选关系如`POTENTIAL_SUBSTITUTE_FOR`必须携带条件、有效期和证据。不能默认对称或传递：A可替代B、B可替代C，不推出A可替代C。产品规格不同、单位不同、适用活动不同都可能使替代不成立。

“停发通知关联了某Mission”只能表示潜在关联。是否会缺货、影响多少件、是否错过交期，由当前在途、库存、需求和规则计算决定，不能把路径结果命名为已确认损失或必然影响。

### 4.3 第三层：全量自动抽图和全局GraphRAG，暂不启动

Microsoft GraphRAG的local search结合实体/关系和原文，global search则使用社区报告回答语料整体主题问题。它们是可评估的方法，不是文档录入必须安装的组件。

当前明确业务线仍以单店、单SKU、单供应商SC01为基准；跨供应商/多SKU图关系在K0可用合成案例研究，但不能据此宣称生产业务已经支持多SKU优化。没有真实多步问题或足够语料时，先建全量图与社区摘要可能增加维护负担而无可测收益。

## 5. 关系事实的质量要求

K0测试关系使用JSON数据文件，先不新增生产图表。每条关系至少包含：

```text
edge_id, store_id,
subject_type, subject_id, predicate, object_type, object_id,
origin_kind(backend/document/manual),
source_record_id 或 source_version_id+source_locator,
valid_from, valid_until,
assertion_status(verified/candidate/rejected),
qualifiers, revision
```

一条关系如果有多份来源，保留来源集合和各自有效区间；不同版本有冲突时分别保存，不以检索分高或LLM自评置信度决定真伪。

权限适用于节点、边和边所依赖的文档证据；仅过滤最后展示文本仍可能泄露关系是否存在。路径中每一条边必须允许当前用户读取，并在同一as_of下有效。文档撤权/过期/归档时，依赖其证据的关系不能继续作为当前有效事实参与扩展。

不把候选抽取关系自动提升成verified。只有确定的backend键、显式来源字段或用户确认才能形成可信关联；自动抽取可以缩小人工检查范围，但不授权采购或永久写记忆。

## 6. K0数据与对照实验范围

### 6.1 首批40份合成经营资料

| 类别 | 数量 | 覆盖重点 |
|---|---:|---|
| 供应商条款和通知 | 12 | 正常交付、部分履约、截单、过期/未来版本、局部替换、同名供应商 |
| 商品资料 | 8 | 储存、包装、保质期、明确替代条件与不能替代的反例 |
| 店铺SOP | 8 | 收货、少货、延迟、临期、角色与例外 |
| 活动资料 | 6 | 商品关联、时间要求、与当前正式需求不同的草稿 |
| 复盘与沟通纪要 | 6 | 事实/意见区分、来源指向、相似案例、因果未证实 |
| 合计 | **40** | 所有资料明确标识模拟，不使用IH私有业务资料 |

在上述40份中安排多格式和异常：至少8 PDF（包含多页表格、纯扫描和混合扫描）、6 DOCX、4 XLSX、4 CSV，其余MD/TXT；格式与主题交叉，不额外把每个格式复制算成新业务案例。解析失败样例、公式无缓存和权限干扰样例必须在manifest中明确预期。

当前范围尚未生成这些文件。K0开始实验后按此数量创建并核验原件和内容hash。

### 6.2 问题集：原60问＋12个关系专项问题

原60问保持精确12、关键词12、同义12、综合8、无答案/冲突8、业务混合8。新增关系专项12问：

- 4问为单步标签/SQL关联即可回答，用于防止把简单问题包装成图能力。
- 4问为2～3步跨文档与业务实体路径。
- 2问为条件边反例，覆盖替代不可传递与时间区间不重叠。
- 2问为图不完整/关系未确认，要求返回证据不足，不能编造完整名单或因果。

共72问：原60分40调参/20冻结验收，关系12分8调参/4冻结验收。核心60组间分布保持不变，报告额外关系组，避免改分母后把效果提升归因错误。

### 6.3 实验阶梯与解释边界

| 对照 | K0要回答的问题 |
|---|---|
| A 元数据＋关键词 | 是否已经足够找到正确资料？ |
| B 同样过滤下的混合检索 | 同义和跨段落问题是否改善？有模型配置时实测，否则明确记为未运行 |
| C SQL实体关联限定＋相同文档检索 | 提升是否仅来自已知实体/适用范围约束？ |
| D 有界关系遍历＋相同文档检索 | 多步路径是否比C额外提供证据召回收益？ |

C与D共享同一组关系事实、权限和生效时间；差别是查询方法，不能只给D更完整的人工答案关系再宣称图算法更优。词法/向量、父块、上下文和生成预算尽可能固定。A→C的改善属于结构化过滤收益，不自动证明需要图数据库。

D首版仅用JSON邻接表/小型内存遍历或PG查询表达有界路径，不部署图数据库；关系来自已有业务字段映射和明确标注的合成资料，不以LLM生成的关系冒充原事实。K0不需要跑Microsoft GraphRAG全量建图。

SQL本身也能表达多步JOIN和递归查询；如果C已经满足问题，不为维持四种方案而造出不存在的能力差异。此时结论可以是“轻量关联足够，暂不建设图数据库”。

评测新增：关系路径正确率、每条边证据可定位率、必需支持片段召回、条件/时间适用正确性、不完整信息处理、人工建边/更新耗时。若图没有改善正确回答，或增加错误路径/维护成本，则不进入生产图实施。

## 7. 对实施计划的影响

- K0新增数据分类表、关系schema、12问专项与C/D对照；原RAilG依赖/解析/OpenSearch兼容检查保留。
- K1/K2维持原文档管理与实体标签；现有业务关系直接读，不建立第二套可变经营事实。
- K3/K4根据K0报告决定是否增加关系引导检索/路径证据；不能提前宣布该部分已采用或已有效。
- 独立图数据库、自动全量抽图、社区摘要列在有条件的后续工作包。原13～21工程日估计未包含完整图系统，若采用另行估算。

## 8. 来源与本轮核查边界

- 本地模型：`backend/app/operations/models.py`（Store/Product/Offer/Stock）、`missions/models.py`、`execution/models.py`。本轮仅读源码，没有迁移或改动数据。
- [Microsoft GraphRAG Query Overview](https://microsoft.github.io/graphrag/query/overview/)：local、global与basic search适用方式。
- [Microsoft GraphRAG Local Search](https://microsoft.github.io/graphrag/query/local_search/)：实体、关系与原文共同组成检索上下文。
- [PostgreSQL 17 WITH Queries](https://www.postgresql.org/docs/17/queries-with.html)：递归查询与路径/循环处理。采用关系模型不意味着必须新增图数据库。

本轮没有运行性能实验、生成合成语料或证实图检索收益。以上内容是开始K0前的数据与方法范围。
