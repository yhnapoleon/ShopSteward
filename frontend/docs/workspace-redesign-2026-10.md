# 前端工作区重构设计（2026-10）

本文是前端重构的实施依据，供实现者（人或 Agent）逐项执行。读者可以不了解之前的对话。基线为 main `87eb193`（本机标签 `qa-baseline-20261014`）；所有改动在个人分支 `jeffrey` 上按阶段分别提交，每一阶段都能单独回退。

## 0. 目的与边界

**要解决的问题。** 2026-10-14 的真实浏览器走查证明：业务数字正确、确认护栏有效、重启不重复采购；但店主看到的是后端的形态——原始日志、UUID、状态码、"分"为单位的金额；同一项委托有两套工作区（任务工作区 / 事项工作区）互相跳转；顶部导航和底部浮条重复；没有模型时建立委托的入口消失；后端停机被误报为"身份未连接"；Agent 的跨会话记忆没有任何界面。

**目标用户。** 课程评审与演示观众为主，但要达到真实店主可用的周到程度：每个数字可追溯，每个动作有反馈，没有需要翻译的内部术语。

**本轮做什么。** 只改前端（`frontend/`）。后端不改；若发现某个效果必须改后端，先记录在第 16 节，不实现。预测面板、时间语义、后端文案结构化按既定决定暂不处理。

**不做什么。** 不动同学分支（`YH`）涉及的文件区域（第 14 节）；不安装新的组件库；不引入远程字体；不把任何模拟逻辑放进前端；不让任何组件绕过后端直接改金额或发起采购。

## 1. 设计判断

一句话：**重构-保留型的经营工作区，面向演示观众，沿用现有暖光磨砂语言；动效克制但在"系统在动"的时刻明确。** 参数：布局变化 5 / 动效 5 / 密度 5（1–10）。

视觉遵循 [`../style.md`](../style.md)，动效遵循 Emil Kowalski 的设计工程规则（本机 skill `emil-design-eng`）。两者冲突时，以 style.md 的材质与排版为准，以 Emil 的动效规则为准。

三条总原则：
1. **先回答店主的三个问题**：要我拍板什么 → 系统在替我盯什么 → 店里现在什么情况。页面结构按这个顺序排。
2. **对话负责意图和过程，卡片负责结果和动作。** 店主的每个动作（确认、改选、暂停、结束、纠正）只在卡片上发生；聊天里的话永远不触发采购。
3. **后端事实到了前端必须变成店主的语言。** 任何事件、状态、金额都经过翻译层；原始标识只在"可追溯依据"的折叠区里出现。

以 SC-01 示例店铺为例，每一步写明店主看到什么、想什么、点什么。实现时逐步对照。

## 3. 信息架构与导航

### 3.1 视图

| 视图 | 路由 | 内容 |
|---|---|---|
| 今日 | `?view=today` | 第 5 节 |
| 跟进 | `?view=following` | 当前店铺全部事项（进行中在前，已结束折叠），每项一行：标题、状态徽章、下一次检查/预计到货、最近一次变化；页首放提醒摘要 |

| 文档中心 | `?view=documents` | 只改一句说明文案 |
| 任务工作区 | `?view=task&mission=…` | 保留为兼容入口，界面上不再链接 |

### 3.2 导航去重

- 顶部导航：品牌、三个视图（今日/跟进/记录）、Agent 入口、**记忆入口（新）**、设置、店铺切换。
- 桌面底部浮条（`.workspace-dock`）在普通模式下不再显示；它的"经营概览"入口由右栏"店铺此刻"卡和事实条承担。
- 演示模式下，底部出现**演示条**（第 10 节）。
- 移动端底部导航保持三项。

### 3.3 入口规则

- 「先试算补货」与「交给我一件事」在今日/跟进页头常驻，两者永远并存；事项助手不可用时「交给我一件事」仍可保存原话，并在卡片内写明。
- 「交给我一件事」弹层（GoalDeck）同时提供：自然语言输入（WorkIntake）与结构化入口「按当前条件开始备货跟进」（startMission）。右下角两张装饰卡改为真正可点的两个入口（备货跟进 / 报价整理），或删除。
- 顶栏「Agent 工作区」按钮进入当前委托所属事项的工作区并打开对话面（`panel=agent`），不再跳到无对话的页面。

## 4. 事项工作区（统一容器）

事项（work item）是唯一容器；备货委托是一种事项。组件 `components/space/SpaceWorkspace.vue` 替换 `WorkWorkspace.vue` 内部对 `TaskWorkspace` 的嵌套使用。`TaskWorkspace.vue` 本身不修改、不删除（第 14 节）。

### 4.1 页头

返回链接；眉标"备货委托 · SC01 sample product"或"我的事项"；标题（委托目标或事项标题）；状态徽章（第 6 节词汇）；次要动作用文字链接：委托详情、暂停/恢复、结束（仅审批角色）。

### 4.2 左栏 = 执行面（按出现顺序）

1. **同步条 `SyncStrip`**：一行，含经营时点、数据同步时间；当 `s.refreshing` 或"推进事件后状态版本未变"时显示脉冲点与"后台正在同步"。
2. **需要处理 `IssueCard`**：沿用现有 `issue` 语义（confirmation/unknown/stale/expired/changed/offline），文案与按钮与现有一致。
3. **变化卡 `ChangeCard`**：方案版本变化时显示。内容：前后建议数量、剩余需求前后值、已执行采购件数（保留）、本次只补的缺口、触发原因（需求修订/到货/销售/依据更新）。数据来自当前方案与前一版方案（`/api/v1/missions/{id}/plans?limit=2`）及账本最近一条 `DEMAND_REVISED`。
4. **方案卡**：复用现有 `DecisionCard`（不改它）；无待确认方案时显示 `OutcomeCard`（等待到货 / 暂无新决定 / 已结束），样式沿用 `.task-outcome`。
5. **采购与到货 `OrdersCard`**：每笔采购单一行：数量 · 金额 · 状态（第 6 节词汇）· 预计到货 · 到货进度条；点开查看编号与回执。替代弹层式回执，弹层保留作为详情。
6. **经营事实 `FactsCard`**：现金/在库/在途/待结算 + 同步时间 + "查看来源"。保留 `data-testid="cash|stock|inbound|receivables"`。
7. **跟进安排**：复用现有 `FollowUpCard`（不改它）。
8. **事项内容**：试算结果（`WorkResult`）、委托条件卡（mission_request → 接受）、澄清卡（`question`，用 `ClarificationCard` 呈现为结构化输入：若问题含"预算/日期/数量/供应商"等词，展示对应快捷字段；否则纯文本）、报价工作区（`QuotationWorkspace`）。
9. **时间线 `TimelineCard`**：第 7 节翻译后的事件，默认 6 条，例行检查折叠，"历次方案与决定"折叠区沿用现有逻辑（读 `/plans`）。
10. 提醒链接、结束委托、页脚说明。

### 4.3 右栏 = 对话面 `ConversationPanel`

一个分段控件切换两条对话：
- **Agent 对话**（委托绑定的 Mission Agent）：复用 `AgentWorkspace.vue`（不改它），它自带运行状态、工具过程、业务成果、对话。
- **事项对话**（事项处理者）：复用 `WorkConversation.vue`。

默认标签：事项有委托且 `session.agentEnabled` 时为 Agent 对话；否则事项对话。两者都保持挂载（`v-show`），切换不丢草稿。`panel=agent` 查询参数打开 Agent 对话。无模型时对应标签内保留现有"暂未启用"说明，输入框禁用。

### 4.4 过程联动

Agent 工具完成（`useAgentConversation().s.activity`）时，左栏对应卡片短暂高亮约 1.1 秒（沿用 `.task-target.target-active` 的做法，映射：facts→事实卡，plan→方案卡，mission→页头，history→时间线，receipt→采购卡）。首次加载与历史回看不重播。

### 4.5 移动端

≤820px：顶部分段「执行 / 对话」，默认执行；事实摘要前置；输入区不被固定元素遮挡。

## 5. 今日页

顺序固定：
1. 页头：标题、副标题、两个入口按钮。
2. **需要你拍板**：只放需要动作的卡（待确认方案、需要补充、需要处理、确认结果待查）。计数徽章只数这些。
3. **系统在盯 `WatchList`**：其余进行中的事项，每项一行（标题、状态徽章、下一次检查或预计到货、最近变化一句话）；没有时显示"暂无跟进中的事项"。
4. **已结束的委托**：折叠，沿用现有。
5. 提醒链接（有 OPEN 提醒时）。
6. 资料与简报：三张入口卡沿用。
7. 七日预测面板：保持现有组件与 DOM，位置移到资料之后；不改其内部。
8. 右栏：店铺此刻（`BusinessFacts`，不改）+ **服务状态 `ServiceStatus`**（第 11 节）。

空店铺（无事项、无委托）时主区显示一张"开始"卡：三步说明 + 两个入口。

## 6. 词汇与状态模型

### 6.1 词汇表（界面只用这些词）

| 词 | 指 | 不再使用 |
|---|---|---|
| 事项 | 店主交给系统的一件事（容器） | 任务、Work |
| 备货委托 | 持续跟进某商品备货的事项 | 委托、Mission、活动备货跟进 |
| 方案 | 一次检查给出的候选比较与建议 | Plan、计划 |
| 采购单 | 店主确认后发出的一笔采购 | 动作、Action、订单 |
| 到货 | 采购单的实际收货 | 入库、inbound |
| 提醒 | 系统发现的风险 | 警报、alert |
| 检查 | 后台按计划或事件触发的一次评估 | 周期检查、job |
| 记忆 | Agent 跨会话记住的内容 | 知识、knowledge |
| 技能 | 可复用的做法（记忆的一类） | skill |

### 6.2 状态徽章（`utils/glossary.ts`）

输入：事项状态、委托状态、方案状态、未决采购单、`business.code`。输出：`{ label, tone }`。优先级从上到下取第一个命中：

| 条件 | 标签 | tone |
|---|---|---|
| 确认结果待查 / 采购结果 UNKNOWN | 需要处理 | amber |
| 方案待确认且可确认 | 需要你拍板 | amber |
| 事项 WAITING_INPUT | 需要你补充 | amber |
| 采购单 QUEUED/EXECUTING | 正在核实采购 | blue |
| 有在途且无待确认方案 | 等待到货 | blue |
| 事项 PROCESSING | 正在处理 | blue |
| 委托 PAUSED | 已暂停 | gray |
| 委托 COMPLETED/CANCELLED 或事项 COMPLETED | 已结束 | gray |
| 事项 CANCELLED | 已停止 | gray |
| 事项 RESULT_READY 且无委托 | 结果已出 | green |
| 委托 ACTIVE | 持续跟进中 | green |

后端 `business.label` 只作为无法匹配时的回退。

### 6.3 标识显示

店铺：演示模式下显示"示例店铺 · 10/14 15:26"（创建时点），其他模式显示尾号。供应商：有名称（供应商资料或寻源记录）时用名称；没有名称的按它对这项委托的角色叫"原供应商"（委托的默认供应商）或"已对接的供应商"（`useShop` 读店铺数据时登记，资料里有真名时替换）；都取不到时才写"供应商 001"（从 `supplier_001` 派生）。UUID、哈希、状态版本只出现在折叠的"可追溯依据"里。

## 7. 时间线翻译规则（`utils/timeline.ts`）

`describeEvent(entry: TimelineEntry) → { title, detail?, tone, icon, routine, references }`。解析失败时 `title = summary` 原样。

| type | summary 形态 | 显示 |
|---|---|---|
| MISSION_CREATED | `Mission created` | 建立备货委托 |
| MISSION_CONTROLLED | `pause` / `resume` / `complete` | 已暂停主动跟进 / 恢复主动跟进 / 结束委托（用户动作） |
| PLAN_CREATED | `推荐采购{n}件；预计支出{分}分，采购后可用现金{分}分，剩余缺口{n}件。` 或 `当前候选均不满足采购约束，未提出采购。` | 新方案：建议补 {n} 件 · 支出 ¥{元} · 采购后现金 ¥{元} · 缺口 {n} 件 / 新方案：没有可行的采购 |
| PLAN_DECIDED | `approve` / `reject` | 你确认了采购 / 你选择本轮不采购（用户动作） |
| CHECK_REQUESTED | `{reason}（任务{id}）` | 你要求重新检查 |
| CHECK_COMPLETED | `检查{STATUS}：{summary}（任务{id}）`；summary ∈ `Candidate comparison saved` / `Existing valid plan reused` / `Mission inactive or an action is pending` / `DATA_STALE` / 其他 | 检查完成：已生成新方案 / 方案无变化（routine） / 有采购待核实，本次跳过 / 数据未更新，未能检查 / 原文；STATUS 只影响 tone：HEALTHY green、ANOMALY amber（含"（这是风险判断，非系统故障）"的 detail）、INCONCLUSIVE gray、SKIPPED gray |
| ALERT_OPENED / ALERT_ESCALATED | `{TYPE}：{summary}` | 发现{提醒名}：{summary} ；TYPE 映射 STOCKOUT_RISK 缺货风险、CASH_CONSTRAINT 现金约束、ACTION_EXCEPTION 采购需核实、DATA_STALE 数据未更新 |
| ALERT_RESOLVED | `{TYPE}：状态版本{n}的新鲜输入确认风险已解除。` | {提醒名}已解除（routine） |
| ALERT_ACKNOWLEDGED | `已知晓{TYPE}；风险尚未解除。` | 你已知晓{提醒名}（用户动作） |
| ACTION_EXECUTING | `采购已登记发送，资金暂时预留。` | 采购单已发出，资金已预留 |
| ACTION_SUCCEEDED | `SUCCEEDED` | 供应商已受理采购 |
| ACTION_UNKNOWN / FAILED / CANCELLED / STALE | 原因或状态 | 采购结果待核实 / 采购未成功 / 采购已取消 / 原方案失效 |
| 其他 | — | summary 原样，tone gray |

分组：连续的 `routine` 事件折叠为一行"{n} 次例行检查，方案无变化 · 最近 {时间}"，可展开。金额显示用 `money()`（分→元）。用户动作用人物图标，系统事件用圆点。简报（`briefing()`）与经营记录都使用同一翻译。

## 8. 记忆面板

入口：顶栏图标按钮「记忆」（移动端在设置旁）。形态：右侧抽屉（原生 `dialog`，从右侧滑入，`--ease-drawer`，≤300ms）。

数据：`GET /api/v1/stores/{store_id}/agent-knowledge` → `items[]: { id, kind: USER|NOTES|SKILL, task_type, version, entries[]: { id, content, required_tools } }`。写入：`POST` 同路径，body `{ kind, task_type, expected_version, operation: add|replace|remove, entry_id?, content?, required_tools? }`，带幂等键（`api()` 第四参数）。写入接口在后端 Agent 未启用时可能返回 503：此时面板只读，并说明"修改记忆需要启用 Agent"。

分区与内容：
- **关于你**（USER）：每条一卡，正文 + 「纠正」（内联编辑后 replace）+ 「删除」（remove，二次确认）。
- **经营笔记**（NOTES）：同上。
- **技能**（SKILL）：标题取内容首句，副行"适用：{task_type} · 依赖工具：{required_tools 翻译}"；「停用」= remove。

空态：解释记忆如何形成（"在对话里说'以后现金至少留 500'，Agent 会记下来；报价纠正会形成整理规则"）。

形成提示：`useAgentConversation` 观察到工具 `memory_edit` 成功完成时，右栏对话内出现一行回执"已记住一条偏好"，顶栏记忆图标显示小点，面板重新读取。

来源与时间：后端条目没有逐条时间和来源字段，面板不伪造；只显示版本号。补字段列入第 16 节。

## 9. 动态 surfaces（A2UI 的前端层）

目的：让 Agent 的结构化产物以"组件组合"的形式动态呈现，同时保证数值来自后端、组件不能发起审批。

- `app/surfaces/catalog.ts`：受信组件目录，首批：`MetricRow`（指标组）、`PlanComparison`（候选表）、`EvidenceList`（依据列表）、`DemandChange`（需求变化）、`QuoteTable`（报价表）、`NextStep`（下一步入口，只能指向既有弹层/路由）、`ClarificationForm`（澄清表单）、`Text`（Markdown 正文，经现有 `MarkdownMessage` 净化）。
- `app/surfaces/types.ts`：`Surface = { version: 1, blocks: Block[] }`，`Block = { component: keyof catalog, props }`。限额：≤24 块；props 只允许目录声明的字段；未知组件整块降级为 `Text`；不允许 HTML、URL 以外的资源。
- `app/surfaces/derive.ts`：从现有结构化结果确定性地生成 surface：`WorkResult`（kind、columns/rows、assumptions、references、calculation）、`BusinessOutcome`（before/after 比较）。这保证今天没有后端改动也能工作；将来后端若在结果里附带 `surface` 字段，渲染器先校验再使用。
- `components/surfaces/SurfaceRenderer.vue`：按 blocks 渲染，进入时 40–60ms 阶梯淡入（仅首次出现，不在后台刷新时重播）。
- 使用位置：事项结果卡、对话中的结果回执、Agent 业务成果。

### 18.1 形态

### 18.2 每一步

1. **说明情况**（`RecoveryBrief.vue`）：全部预填，店主确认即可。
   - 问题句：按触发原因和"不补货的七天"推演生成，例如"原订单晚到：不补的话 10/21 起缺货，7 天共缺 40 件。"推演与求解器同一套日结规则（`projectWithout`：原订单按预计到货计入，已逾期的不计）。可在"修改"里改写，提交为 Case 目标。
   - 预算：可用现金 − 现金底线，旁注来源；现金已到底线时写明这次买不了。可在"修改"里改。
   - 7 天需求：一个分段控件。第一项是已启用的日预测（"按预测"，提交时不带日需求，由后端读预测）；没有日预测时是当前方案的需求假设按 7 天均摊（"按估算"）。第二项"每天 N 件"可改件数。
   - 首日结算：只在"修改"里显示。按经营时钟取第一天结束前一秒（与后端用预测时的口径一致），显示本地时间；每次修订都按当时时钟重新生成，店主不用填。
   - 资料：只写"资料在档：3 家"和名称。演示模式下没有资料时，打开说明即载入示例资料，自动载入失败才出现"载入示例资料"链接；非演示模式不载入示例资料。
   - 七天条（`RecoveryDays.vue`）：只在不补货仍有缺口时出现。每天的需求，琥珀色是卖不出去的部分，卡车标记在到货日的柱顶；没有图例，含义写在图的无障碍名称里。
   - 七天内不缺货时主按钮是"关闭"，比价降为文字链接"仍要比价"。有缺口时左下的"关闭"只关闭说明，不记录任何决定。
2. **找货比价**（`RecoveryCompare.vue`）：确认后依次建 Case、分析、寻源（有资料且后端开放寻源时）。
   - 读资料时标题"正在读 3 家供应商的资料"，逐家一行：读完前是灰色占位条，读完写单价、起订、每箱、交期，或不配送等原因。
   - 求解器为每家的每个数量都列一个候选（预算 700 元时一家就有五六个），这里按供应商归并，放在与方案卡同一套的浅色槽里，选中行由一块底板滑过去。每家一行显示它的最佳数量（缺货最少、再花钱最少，与求解器推荐的排序相同）、花费、7 天缺货和到货日（有交期时写"9/8 到"，没有交期时写"9/9 前到"）；"推荐"标在供应商上，改选数量不会消失。选中那家下方是数量档：只给最佳档前后各一档，每档带"¥ · 缺 N"，并标出推荐的那一档。"等原订单"（没有原订单时写"这次不补"）是一行；被资料排除或全部不可行的供应商列在槽下方并写原因。
   - 本次应急补货排除过的供应商不出现（拒单、撤回、只给一部分，或店主选了"不找…"），推荐按剩下的选项重算；全都排除了时标题写"没有别的供应商可比"，有资料时主按钮是"重新找货"。
   - 标题由求解结果确定地生成（"百川批发补 40 件最合适"），副句给数字（"7 天缺货 40 → 0 件 · 花 ¥380"）。"为什么这样比"（模型解释）与"每家资料怎么读的"（引文）折叠在下面；中文界面只显示中文条目，条目里的供应商代号换成名称。
3. **采用并确认**（`RecoveryConfirm.vue`）：主按钮写"用百川批发补 40 件"。同时有操作和审批权限时，一次点击先生成待确认方案、刷新后直接打开页面现有的确认弹窗；只有操作权限时停在这一步，进度标"等审批"，右下是状态字"等有审批权限的人确认"。确认步写明由谁发单（18.4"谁来发单"）；暂时不能确认时只写当前成立的那一条原因（例如"经营数据还在同步，同步后就能确认。"）。"换一家"回到比较，可用"不换了，回去确认"返回；另选一家时先按当前情况重新比价（第一次采用已让委托版本加一，原比较不能再用），再采用新比较里同一家同数量的选项，没有了就请店主重选。在弹窗里确认后，卡片立即重读 Case，并按方案认出后端刚建的订单，直接进入发单。
4. **发单并登记回复**（`RecoveryOrder.vue`）：回复前是订单信息与"复制"；有回复后订单收成一行"订单已发 · 复制"，下面是回执（复用 `SupplierReceipt.vue`）。撤回用文字链接"撤回这笔订单…"，再确认一次。
   - 回复只给一部分：标题"百川批发只能给 10 件，订单是 40 件"，副句"订单 40 件 · 对方给 10 件"；回复框收在文字链接"登记新回复"后面；主按钮上方一行后果"只付 ¥95，余下 ¥285 释放；还缺 30 件，之后可以找别家补。"，主按钮"按对方数量成交（10 件）"（后端 `partial-acceptance`：只付这 10 件，余额释放）。成交后卡片回到比价：标题"百川批发只确认了 10 件"，副句"已按 10 件成交 · 还缺 30 件"，主按钮"缺的找别家补上"——在同一个 Case 里排除这家、修订并重新比价，再采用一家；已成交的 10 件列在卡片里，可直接登记到货（第 5 步）。"撤回整单，找别家补 40 件"为文字链接（撤回后同样排除这家重新比价）。
   - 拒单：订单关闭、资金释放，卡片回到比价：标题"百川批发拒单了"，副句"预留的 ¥380 已退回 · 还缺 40 件"，主按钮"不找百川批发，重新比价"。
   - 只有操作权限时不能登记回复，右下是状态字"等有审批权限的人登记回复"，进度标"等审批"。
5. **登记到货**（`RecoveryReceive.vue`、`RecoveryPurchases.vue`）：店主自己发的单写"百川批发已确认 40 件，货到后请登记"，可分次登记；系统直接下单的写"到货后自动入库，不需要你操作"；等原订单的列出原订单与预计到货，并可"改主意，找别家补"。
   - 本次应急补货里已买到、还没到齐的其他采购（例如部分成交的 10 件），在比价、确认、发单、到货各步都列成一行"百川批发 10 件 · 9/8 到"，带文字链接"登记到货"（只有店主发的单可登记）。如果这次登记会让后端在缺口还没补上时结案，登记前先说一句"登记后，这次应急补货按 N 件结束；要补缺口先点「缺的找别家补上」。"（N 为本次已买到的全部件数）。
   - 后端要等所有采购都到齐才结算：全部到齐后写"货已到齐，正在结算结果"；当前这笔到齐、另一笔还没登记时写"还有一笔货没登记"；部分成交后又选了等待，写"等已买到的货到齐"。
   - 没有原订单时选的"这次不补"停在"决定这次不补"：后端不会自行结束这件事，每天的补货建议一直暂停，所以卡片标题"这次不补"，副句"没有在途的原订单。结束后，系统恢复每天的补货建议。"，主按钮"结束这次应急补货"。
6. **结果**（`RecoveryOutcome.vue`）：以后端结算时记下的 `outcome` 为准：预计缺货前 → 后（"7 天合计（预计）"）、花了多少、到货 x/n。两笔以上采购时按供应商分开写"补到 40 件（百川批发 10 + 安和商贸 30）"（后端的 `planned_qty` 是所有订单之和，不当作订单量）；只有一笔且只成交一部分时写"百川批发确认的 10 件已到货（订单 40 件）"。缺货数是后端按同一套七天推演的值，写"预计"。收起时是一行："应急补货完成 · 百川批发 40 件已到货 · 预计缺货 40 → 0 件 · 花了 ¥380"。店主手动结束的事项没有 `outcome`，只写当前这笔买了什么、是否在途。

### 18.3 页面其余部分

- **方案位不重复**：应急补货进行中、又没有别的决定时，方案位不显示（待确认的应急方案、店主发单的订单卡、"等待到货"结果卡都由应急卡承担）；还有常规方案可确认或另有店主发单的订单时照常显示。方案刚确认、卡片还没重读 Case 时，按方案认出后端刚建的订单，不在方案位重复出现。
- **到货登记归应急卡**：应急补货进行中，它的每一笔采购只在应急卡里登记（`useRecoveryLaunch().holds()`；`useShop().awaitingArrival` 跳过这些订单），这样卡片能在登记会结案时先说明。页面的到货卡只列其余店主发的订单：标签"货到后请登记"，标题"{供应商} N 件"，两项事实（预计到货、到货进度）；应急补货进行中或方案位上有方案（可确认的，或重新核对期间保留的）时，它的"登记到货"降为次按钮，也不展开回执；没有操作权限时写状态字"等有操作权限的人登记到货"。
- **供应商名称**：`utils/glossary.ts` 有门店供应商名称登记（来自供应商资料和寻源记录，换店清空），`supplierDisplayName` 先查它。`useShop` 读店铺数据时同时读供应商资料（不阻塞刷新；失败后从 5 秒起翻倍退避，最多 5 分钟），今日页读应急事项时也登记寻源读出的名称，所以确认弹窗、方案卡、采购行、订单卡、到货卡、今日卡从第一屏起就写"百川批发"。没有名称的供应商按它对这项委托的角色叫"原供应商"（委托的默认供应商）或"已对接的供应商"，资料里有真名时替换。名称写进中文句子时用 `utils/recovery.ts` 的 `named()`：以字母或数字开头或结尾的名称与相邻汉字之间留一个空格（"用供应商 001 补 40 件"，与"40 件"的写法一致），中文名称照常相连，英文句子不变。
- **状态词**：店主自己发的单在途时，页头徽章、今日与跟进的事项行、采购行都写"货到后请登记"（`statusBadge`/`workBadge` 的 `ownerRecordsArrival`、`orderStatus`）；页头徽章也算应急卡里登记的那几笔。
- **一屏一个主按钮**：应急补货进行中时，若还有可确认的常规方案，方案卡收成一行"常规方案：建议补 20 件 · ¥200"加文字链接"核对 20 件采购"（仍打开同一个确认弹窗）；应急补货结束后方案卡恢复原样。同一时段问题卡、店主发单的订单卡、页面到货卡的按钮都降为次按钮。应急方案过期或依据变化由应急卡说明，页面不再另出"方案已过期 / 方案待更新"问题卡（`pages/index.vue` 的 `restockOwnsPlan`）；经营数据未同步关乎整店，照常提示。提醒弹层的"找别家补"是次按钮。常规方案收成一行只出现在采用之前：店主一旦在应急补货里做了决定（采用方案或选择等待），后端在事项结束前跳过例行检查，不会再产生可确认的常规方案；采用过的方案失效时，由卡片按后端的原因说明并给"重新比价"。
- **键盘**：比较是一个单选组，Tab 进入选中的那一行，方向键移动选择（底板瞬切，不播动画），回车或空格作用于按钮；数量档、需求分段、结果行、页头入口都是按钮，可聚焦。
- **单价**带分（¥9.50），金额沿用全站 `money()`；数字与单位、"40 → 0 件"整组不换行。
- **订单写入可安全重试**：登记回复、撤回、按对方数量成交、登记到货遇断线或 5xx 时，`useShop` 把这次写入记在 sessionStorage `ss.order-writes`。订单读回来还是原样时，同样的写入沿用原幂等键重发，后端按第一次的结果答复，不会重复入账；内容不同的写入要先核实上一次；订单已经变了就放下这条记录。
- **委托时间线**：后端写的应急补货固定句（方案过期或依据变化、方案未采用、选择等原订单、结算、部分成交、登记到货等）按产品叫法改写，例如结算句写成"应急补货完成：补到 40 件，已全部到货"，"例行补货暂停"写成"应急补货进行中，每天的补货建议暂停"。没有登记的句子原样显示。
- 旧任务页（`?view=task`）的"供应异常应对"面板不变。

### 18.4 与要求的差异和取舍

- **部分回复**：10-18 时后端不能只收下一部分，前端按"撤回整单，在同一事项里排除这家重新比价"实现（用户当日确认）。YH 的 #25 支持部分成交后改为：先按对方数量成交，缺的再找别家；撤回整单保留为文字链接。
- **结果阶段**：10-18 时后端从不把 Case 标成完成，前端按全部到货判定（用户当日确认）。#25 之后由后端结算（`RESOLVED` + `outcome`），前端只显示后端的结果，全部采购到齐但还没结算时写"正在结算"。
- **拒单、撤回后不新建 Case**：在原 Case 上修订（排除这家）再比价，进度和记录留在一件事里；从采购行或今日页触发、且没有进行中的应急补货时才新建 Case。后端在采用新报价之前，Case 的 `action_id` 一直指向旧订单，`flowState` 以"Case 在那之后有没有新版本"区分；"当前这笔"只认当前版本的采购。
- **排除供应商**：寻源会重读所有在档供应商，并把读出的都放进比较（`sourcing/run.py`）。前端在寻源结束后自动再修订一次去掉被排除的供应商。被排除的有两类：Case 采购记录里拒单、撤回、只给一部分的供应商（任何浏览器都能推出），以及从入口带来、或店主选了"不找…"的供应商（存在本浏览器的 sessionStorage，每个 Case 一个列表）。比较里不显示被排除的供应商，推荐按剩下的选项重算。
- **自动跟进开关不再出现在应急卡里**：开启后约 15 分钟会把 Case 改成"需重新分析"，与"到货即结果"冲突；旧面板保留该开关。
- **过期**：比价结果超过有效期（#25 起默认 30 分钟，采用后从采用时刻起算）、采用过的方案失效（后端给出 `recheck_reason`）、或经营时钟推进使需求日期失效时，主按钮为"重新比价"（按当前时钟重排需求后修订并分析）；所有报价都因过期不可行时为"重新找货"。副句只写一个原因：比价结果过了有效期写"比价结果已超过有效期。"，经营数据变了写"比价之后经营数据有变化，比价结果不再成立。"。
- **拒绝方案**：有审批权限的人在确认弹窗里拒绝应急方案后，事项继续占着这件事（`routine_paused`）。卡片标题"你没有采用这份应急方案"，副句"结束这次应急补货后，系统才恢复每天的补货建议"，主按钮"重新比价"，文字链接"结束这次应急补货"。
- **没有模型时**：寻源返回 `SOURCING_MODEL_NOT_CONFIGURED`，卡片写"现在读不了供应商资料；先比较已有的报价。"，仍可比较在档报价并走完后续步骤。

### 18.12 第二轮（2026-10-19）

**为什么有第二轮。** 第一轮完成后做了四路只读复审（代码正确性、设计与交互、测试失败归因、后端差距）。结论：形态对，骨架到了产品级；但状态机只读了后端事实的一半（多笔采购、多次排除、确认后的过渡都会出错），视觉层级偏弱（标题 21px，决定性数字是灰色小字，页面到货卡压过应急卡），同一件事有几种叫法，周边卡片还会冒出第二个主按钮。第二轮分"状态机与数据流"和"视觉层级、交互与文案"两路改完后接线，再做一次独立审查（20 条：5 条 P0、10 条 P1、5 条 P2），全部修完。改动在 jeffrey 的工作区，未提交、未推送。

**状态机与数据流**（`utils/recovery.ts`、`composables/useRecoveryFlow.ts`、`useRecoveryCase.ts`、`useRecoveryLaunch.ts`、`useShop.ts`）
- 阶段读 Case 的全部采购：`purchasesOf()` 合并 Case 的 `purchases[]` 与店铺订单列表（取较新的状态、较大的到货数），"当前这笔"只认当前版本的采购；结算要等所有采购到齐（`settling`），当前这笔到齐而另一笔没登记时写"还有一笔货没登记"。
- 确认后的过渡：后端在批准时同步建出订单，`caseAction()` 在 Case 重读之前就按 `plan_id` 找到它；弹窗确认成功即重读 Case（`useShop` 的 `s.decided`）。卡片直接进入发单，不再停在确认步、误报"另一笔采购还没处理完"，方案位也不再冒出同一笔订单的发单卡。
- 排除是集合：拒单、撤回、只给一部分的供应商从采购记录推出，店主选"不找…"的存进 sessionStorage 列表；比较去掉它们后重算推荐（`withoutSuppliers()`），全都排除时写"没有别的供应商可比"。
- "换一家"后再采用：先按当前情况重新比价（第一次采用已让委托版本加一），再采用新比较里同一家同数量的选项；采用遇 `PLAN_VERSION_CONFLICT`（例行检查刚换了委托的当前方案）时，重读后再试一次。
- 部分成交后选等待：已成交的货仍列在卡片里可登记，等待阶段按已买到的货判断是否到齐（"等已买到的货到齐"）。
- 谁在做：发单步看审批权限、到货步看操作权限，没有权限时进度标"等审批"（`FlowProgress` 新增 `other`）；本页调用超过 300 ms 才显示"系统在做"，采用、等待、结束、登记期间选项不收起。
- 写入可安全重试：Case 写入只在回音确实丢失后显示"结果还没确认"；订单写入（登记回复、撤回、按对方数量成交、登记到货）记在 sessionStorage `ss.order-writes`，订单读回来没变之前，同样的写入沿用原幂等键，不会重复入账。
- 读取不倒退：`useRecoveryCase` 给读写编号，采用之前发出、之后才回来的旧读取不会把卡片拉回比较；选最新 Case 时排除已结算的。
- 到货登记归应急卡：应急补货进行中，它的每一笔采购只在卡片里登记（`useRecoveryLaunch().holds()`，`useShop().awaitingArrival` 跳过这些订单）；登记会让后端在缺口未补时结案的，登记前先说明（`endsCaseWith()`），后果句里的件数是本次已买到的全部件数。

### 18.15 录制前修复（2026-10-21，main `ec76043` 之后）

**为什么。** 用真实系统录英文推广片前的终检发现几类会入镜的问题：同屏两套时钟（经营时点与墙钟）、版本号与内部编号、"过一天"或店主登记后方案位闪琥珀"需要处理"或"建议补货 0 件"、常规单确认后回执不见且页面下跳、今日页同屏两个主按钮、演示条压住对话末行、弹窗关闭时遮罩先消失。本节记录对事项页与今日页的调整，只改 `frontend/`。

**改了什么**

- **采购一个说法。** 采购行、历次方案、采购回执弹窗用同一规则：编号取 `external_order_id`，没有就取订单消息的 PO 号，都没有不显示，不再露出内部 ID；拒单写"供应商拒单"，部分成交写"只确认了一部分 · N 件"，与回执组件同词；原因经 `utils/timeline.ts purchaseReason()` 写成人话，未收录的原因码不显示。
- **重新核对窗口**（`useSpace.ts usePlanRecheck()`）。"过一天"后 90 s 内，店主登记回复、登记到货、按对方数量成交、撤回订单后 30 s 内，方案过期是预期的重新核对。事项页：方案有采购建议时保留禁用的方案卡，没有时保留原来的到货卡或状态卡，上面一行"正在重新核对方案…"；方案位上有方案时，到货卡保持次要，不展开回执。今日页同一规则：不出"需要处理"卡、不加计数；同一委托的事项卡保留原来那一行（后端此时把它写成 `PLAN_STALE`），说明换成"正在重新核对方案…"。过了窗口新方案仍没到，两页都照常显示问题。
- **常规单原位推进。** 供应商确认后，到货卡带着回执占订单卡原来的位置；拒单回执留到店主下一步，其间可确认的常规方案收成一行。下一个状态占同一个槽位，浏览器的滚动锚定不再把页面往下推。
- **今日页一个主按钮。** 应急卡只有一句标题，不另加标签。拒单或采购失败时它领头，同一委托待确认的常规方案收成它下方一行，链接"核对 N 件采购"与事项页的同名链接一样，打开该事项并弹出确认。补不上缺口、现金不够、原订单晚到时常规方案仍可执行：事项卡领头，"找别家补"降为次按钮，与事项页（方案卡为主，页头"应急补货"是文字链接）一致。
- **弹窗退场。** `AppDialog.vue` 关闭时立即结束模态，同时插入一层与 `::backdrop` 同样式的遮罩，遮罩与面板一起在 150 ms 内淡出。
- **演示条不压对话末行。** Agent 对话与事项对话只有在自己的框里滚动时，末尾才留出演示条占的 70 px（由 `composables/useOverflowing.ts` 判断）；空对话、短对话不多留白。
- **去掉常驻说明与内部标识。** 删去今日页右栏两句、跟进列表"需要你的排在前面"、Agent 对话空态两句、交代框两句、结果卡与采购回执弹窗底部各一句等。预测链接、预测面板顶部、试算卡、修订回执与报价结果不再显示版本号、内部 ID 与哈希。
