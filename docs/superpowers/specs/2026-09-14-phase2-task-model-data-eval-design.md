# ShopSteward 第二阶段范围设计：补货工具决策 SFT

版本：v0.2，2026-09-14。状态：团队讨论稿，尚未实施。

本版本依据用户对首轮 SFT 范围过大的反馈收窄：只训练工具选择、参数绑定和必要澄清。详细任务、数据、Eval、实验、工程接入、工作包和讨论议题见[二阶段详细计划](../plans/2026-09-14-phase2-sft-data-eval-plan.md)。本文不安排人员分工。

## 1. 阶段目标

在已有 Mission 的补货对话中，用户可以询问数量上限的假设影响，或明确要求修改本次上限。自部署模型识别正确动作并给出参数，业务工具真实执行，模板展示试算结果或新的待确认方案。

同时建立可重放、可评测、可追溯的数据流水线，完成基础模型与 SFT 的公平对照。工程闭环与训练增益分别验收；未观察到增益时提交负结果，不以训练完成代替效果改善。

| 项目 | 本轮要求 |
|---|---|
| 可用结果 | 已有 Mission 中自然语言驱动真实试算或正式方案修订 |
| 功能成功 | 动作、参数、业务状态、展示正确，延迟与成本可测 |
| MVP 必需项 | 有效上下文、受限决策、业务执行、结果模板、最小 Eval |
| 后续增强 | 无 Mission 通用事项、多步恢复、报告 SFT、DPO、多 SKU 经营优化 |
| 下一步产物 | 两个意图对照案例真实执行与 50 个开发 episode |

## 2. 范围边界

- 首轮 SFT 只覆盖“补货场景下的工具选择、参数绑定、必要澄清”。
- 首轮入口是已有 Mission 的用户对话；无 Mission 的通用事项处理器不作为本轮依赖。
- 不训练开放式经营分析、预测计算、长报告生成、通用异常诊断或自主采购。
- 所有业务执行仍走现有授权、版本和幂等协议；模型不能提供服务密钥或审批凭据。
- 实际经营金额继续使用整数分；采购数量沿用后端严格整数及范围约束。
- 允许使用远程 GPU；具体租赁规格、预算和实际运行需在短跑结果基础上确定。
- Python 版本下限沿用项目 `>=3.11`；训练环境与业务应用环境分开锁定依赖。

现有 v6 预测模型负责预测数值；本轮语言模型训练学习如何选择工具。模板或原通用 Agent 负责结果组织和范围外请求。原技能学习可后续单独对照，不与参数更新混为一项效果。

## 3. 选择的架构

采用“固定上下文投影 → 模型一次受限决策 → 现有业务工具 → 确定性结果模板”。

固定流程读取当前 Mission/Plan；模型输出一个动作。允许动作是 `evaluate_plan`、`revise_plan`、`clarify`，以及拟新增的运行时控制动作 `handoff`、`no_action`。每个 episode 最多一次澄清及一次回复；复杂恢复不进入首轮 SFT。

不以单纯意图分类器作为唯一交付，也不让首轮模型承担整条开放式 Agent 链路。规则路由作为基线，检验微调是否有必要。

## 4. 语义契约

| 请求 | 正确行为 |
|---|---|
| “如果最多买 20 件，会怎样？” | 只读试算，不修改正式方案 |
| “把本次采购上限改成 20 件” | 生成新的待确认方案，不执行采购 |
| “先别改，只看上限 20 的结果” | 只读试算 |
| “把上限调低一些” | 询问缺失数量 |
| “这次不用改了” | 停止本请求，不取消整个 Mission 或回滚已完成修改 |
| “做一份季度经营分析” | 转通用路径 |

上限不等于精确采购量，0 不等于 null；无包装信息不能把箱当件。模型输出 ID、版本和数值必须符合可见上下文，执行器不能静默纠正后给模型计为正确。

正式修订受现有后端用户来源与关键词校验影响。首轮要求当前有效用户消息完整表达修改意图和数量；跨消息自然授权聚合另作后端变更讨论。语义正确但后端拒绝要记为集成问题和产品失败，不能通过伪造用户消息绕过。

## 5. 数据与 Eval 原则

数据从人工种子、可重放业务测试、经过验证的 teacher 候选和去凭据真实轨迹获得。先按来源血缘划分 train/dev/test，再生成训练变体；同源改写、失败修复和多轮拆分不能跨分区。

标准轨迹保存状态、版本、来源、实际回执和校验；训练投影只保留可见输入与正确目标动作。隐藏 oracle、未来状态和密钥不进入输入。只对经过验证的 assistant 目标计算 loss。

评测分为单步决策与真实执行 episode；业务状态及数量/金额用确定性断言，澄清语义用明确 rubric 辅助复核。模型独立结果、后端拦截、系统兜底、基础设施错误分别记录。只转交或一直澄清不能算核心任务成功。

建议先做 50 个开发 episode，再扩至 200 个 dev 和 300 个 test；按任务和来源家族报告，数量不作为统计充分性保证。具体指标定义、分母和验收讨论值见详细计划第 6 章。

## 6. 模型和训练预算

首轮以 7–8B instruct 模型为主候选，3–4B/14B 先做可选容量对照。详细计划给出 Qwen3-8B 作为可验证候选，最终 checkpoint 根据中文语义、工具协议、许可证和短跑表现固定。

训练由 100–300 条链路短跑开始，再做 1,000 → 3,000 条实验，有 dev 收益后才扩到 5,000–8,000 条。数据量是工作预算，不是达标承诺；另报有效 episode、场景家族和处理 token。

默认 LoRA，具体参数、精度、mask 和资源由短跑核实。保留固定 base/SFT 对照；无增益时先查数据、模板、上下文和接口，再决定补数或换大模型。首轮不要求 DPO 或全参数训练。

## 7. 可复用代码与必要增量

复用 `agent/src/shopsteward_agent/model.py`、`runtime.py`、`backend/app/agent_bridge/composition.py`、`tools.py`、业务集成测试及任务工作区。新增受限策略分支、上下文投影、模板、轨迹采集与研究工具。

不直接用学生模型替换全部通用 Agent。策略模式限定实验环境/会话，业务执行始终复用现有网关；写入成功或状态未知时先核对回执再决定回退。

研究目录与生产执行代码分开，研究 runner 调用同一契约和业务适配，不建立第二套业务规则。训练依赖使用独立环境。
