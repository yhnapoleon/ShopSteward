# ShopSteward 技术选型与受评估约束的自进化设计

日期：2026-10-08（Asia/Shanghai）。状态：选型已定；X1 已实现并用真实模型跑过，X2 已完成一次试点，结果见 [2026-10-08 评测与演化报告](../../reports/2026-10-08-strategy-evaluation.md)；X3 以后尚未实现。代码基线：`YH` / HEAD `30bed9f` 加工作区未提交改动，包含 2026-10-08 接入的协作策略层。

2026-10-08 项目负责人确认了三件事：用 DeepSeek 做真实运行，先小批量再放大；第 5.4 节的优化用分数按本文定义；第 7.6 节的 Skill 准入门槛可以放宽。同时明确本项目的目标是在理想条件下跑通一次完整演示、完成概念验证，不追求上线级的稳定性，其他门槛也可以相应放宽。因此本文里的统计门槛都按演示级执行：如实报告计数和失败，不要求统计意义上的证明。

读者是项目组成员和后续实施者。本文可以独立阅读；需要细节时再看[统一设计 v1.2](2026-09-30-next-phase-integrated-design.md)、[自进化总设计](2026-10-03-memory-skill-workflow-evolution-design.md)和 [Skill 质量 Rubric](2026-10-03-skill-quality-rubric.md)。文中的数量、预算和阈值都是工程初值，不是已验证的结论；本文没有产生任何实验成绩。

## 0. 结论

引入三项技术，有条件引入一项，两项只采用其方法或结论，其余暂缓或不引入。

| 技术 | 决定 | 在本项目中做什么 | 阶段 |
|---|---|---|---|
| GEPA（反思式遗传—帕累托文本优化） | 引入 | 唯一的演化引擎：离线演化专家提示词和基线 Skill 的文本 | X2、X3 |
| MAST（多 Agent 失败分类） | 引入 | 协作诊断的失败标签词表 | X1 |
| Agent Skills（`SKILL.md` 开放格式） | 引入 | 基线 Skill 的存放与导出格式 | X3 |
| OR-Tools CP-SAT | 有条件引入 | 多 SKU 联合备货的组合选择；只在做该扩展时引入 | X4 |
| SkillRevise | 只采用方法 | 从已审基线出发、按轨迹修订、重新执行后择优；由 GEPA 实现，不另建循环 | X3 |
| 多 Agent 规模化研究 | 只采用结论 | 预注册的策略对照假设和用例特征记录 | X1 |
| A2UI | 暂缓 | 现有计划 Task 11 启动时重新核对版本 | — |
| OpenTelemetry GenAI 规范、外部记忆框架、通用语义压缩、LLM 协调器、强化学习检索、自修改代码 | 不引入 | 理由和复议条件见第 3.6 节 | — |

设计原则只有一条：**一个引擎、一种制品、一道门**。所有“自进化”都是对带版本的文本制品做离线优化，由同一个优化器产生候选，候选经同一套评测和同一道发布门槛后，靠配置启用。评测器、金标和业务硬规则永远不是优化对象。

下一步先做 X1（评测底座，约 3–4 人日）和 X2（GEPA 试点，约 2–3 人日，另需模型额度）。这两步能在 10 月 25 日课程截止前产出两组实测：四种协作策略的对照，以及提示词演化前后的对照。

需要项目组确认三件事：

1. 用于真实运行的模型密钥和额度（第 5.5、6.3 节）。
2. 优化用分数的定义（第 5.4 节），它决定优化器朝哪里走。
3. Skill 准入门槛是否分两档（第 7.6 节）；按现有门槛，小样本下几乎没有 Skill 能被启用。

## 1. 现状与缺口

已有两条实现线。协作线：Case 专家可按四种策略运行，分别是固定流程（R0）、单 Agent（R1）、固定三专家（R2）、按需专家加一次定向补查（R3）；结果由代码合并，一次运行可以导出为评分记录。学习线：Skill 的采集、提炼、质量卡、准入、检索、撤销已有竖切实现。细节见[运行手册](../../runbooks/next-phase-agent-recovery.md)和 [Skill 学习运行说明](../../runbooks/skill-learning.md)。

三个缺口阻碍继续扩展：

1. **没有任何实测结果。** 所有验证都用模拟模型。四种策略哪个更好、提示词改动有没有用，都没有数据。
2. **没有一个 Skill 能被启用。** [evaluation.py](../../../backend/app/learning/evaluation.py) 的 `replay_suite` 需要调用方提供隔离执行函数，而这个函数不存在。此外门槛本身在小样本下很难满足，见第 7.6 节。
3. **提示词写死在代码里。** 专家的提问在 [context_cases.py](../../../backend/app/agent_bridge/context_cases.py)，输出约定在 [runner.py](../../../agent/src/shopsteward_agent/cases/runner.py)。它们没有版本，无法对比，也无法交给优化器。

本设计的目标是补上这三个缺口，并让之后每一步扩展都有同一把尺子。不在范围内的事：改业务硬规则和采购确认链路；训练或微调模型；让系统在线、自动地修改自己；放宽用户同意和数据隔离。

## 2. 选型依据

| 证据 | 核对程度 | 对设计的含义 |
|---|---|---|
| [SkillsBench](https://arxiv.org/html/2602.12670v1)：84 个任务、7 种配置。人工整理的 Skill 通过率 40.6%，不用 Skill 24.3%，模型自写的 Skill 21.0% | 论文页面 | 未经执行验证的模型自写 Skill 不可信。我们的提炼来自真实轨迹，设定不完全相同，但同样没有执行验证 |
| [SkillRevise](https://arxiv.org/abs/2606.01139)：诊断轨迹、取修复原则、做锚定执行的修改、重新执行后保留最优；SkillsBench 成功率 36.05% 升到 61.63% | 论文摘要页 | 从一个不完美的初稿出发做修订，比从零生成可靠 |
| [自改进 Agent 的脆弱性](https://arxiv.org/abs/2608.18066)：自改进会放大评测噪声，结果依赖任务顺序 | 论文摘要页 | 每个结论至少两次重复、两个优化器种子，并报告区间 |
| [GEPA](https://github.com/gepa-ai/gepa)：读取完整执行轨迹，用语言模型反思并改写文本，维护帕累托前沿；自带用同一机制演化 `SKILL.md` 的流程 | 项目 README、适配器源码、PyPI 元数据 | 一个引擎可以同时覆盖提示词和 Skill 文本，且评测次数预算在百次量级 |
| [多 Agent 规模化研究](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)：180 种配置。可并行任务上集中式协作提升 80.9%，顺序型任务上所有多 Agent 变体下降 39%–70%；独立式放大错误 17.2 倍，集中式 4.4 倍 | 官方博客 | 我们的集中式代码合并方向正确；恢复分析偏顺序型，多 Agent 未必占优，必须实测 |
| [MAST](https://arxiv.org/html/2503.13657v3)：14 种失败模式、3 大类，1,642 条标注轨迹，标注一致性 κ=0.88 | 论文页面 | 可直接用作失败标签词表 |
| [Agent Skills 规范](https://agentskills.io/specification)：`SKILL.md` 加 YAML 头，`name` 最长 64 字符，`description` 最长 1024 字符 | 规范原文 | 导出成本低，格式约束明确 |
| A2UI v1.0 为候选版，`@a2ui/web_core` 已到 0.10.x | 二手检索结果 | 自进化总设计定的 v0.9.1 目标已过时，启动前要重新核对 |
| OpenTelemetry GenAI 规范仍标为 Development | 二手文章 | 不拿它当我们的轨迹契约 |

## 3. 选型决定与替代方案

### 3.1 演化引擎：GEPA

选 GEPA 的三个理由。第一，它用文字反馈而不是单个分数来改文本，我们的评分器正好能给出“哪条检查没过、为什么”。第二，它通过适配器接入任意系统，不要求把 Agent 改写成某个框架的程序。第三，它是遗传搜索加帕累托选择，质量和调用成本可以同时作为目标。

没有选的方案：把专家改写成 DSPy 程序再用其优化器，改动面大且与现有运行时、预算账本重复；手工改提示词，没有可复现的搜索过程和对照；强化学习或微调，需要的样本量和算力超出本项目，自进化总设计也已排除。

GEPA 以遗传搜索为核心。它能否算作课程要求的“演化计算”技术组，需要向任课老师确认；它优化的是 Agent 的文本，不是经营资源。

### 3.2 Skill：基线制品加修订

不再以“从用户轨迹从零提炼”为主路径，改为：人工写好并审过的基线 Skill 作为产品内容随代码发布，再用 GEPA 按执行反馈修订。SkillRevise 的做法由 GEPA 的反思、修改、小批验证、择优流程实现，另外补一份固定的修复原则清单给反思模型，不单独实现第二套循环。

按用户的提炼路径保留，但重新定位，见第 7.5 节。

### 3.3 失败标签：MAST

统一设计 v1.2 第 19.11 节要求失败按可定位的阶段归因。MAST 提供了有标注一致性数据支撑的词表。我们的架构没有 Agent 之间的自由对话，其中几种模式在结构上不会出现，这本身可以写进报告的设计论证。

### 3.4 Skill 格式：Agent Skills

`SkillSpec` 的 JSON 仍是权威结构，`SKILL.md` 由它生成。这样基线 Skill 可以被人直接阅读和评审，也能被其他支持该格式的工具读取。首版只导出，不导入外部 Skill。

### 3.5 组合优化：CP-SAT，有条件

统一设计 v1.2 第 21.1 节的多 SKU 联合备货限定在 3 个 SKU、每个至多 6 个候选，共 216 种组合，枚举足够。只有当 SKU 数量超过这个范围，或加入跨 SKU 的供应商约束时，才值得引入求解器。因此 CP-SAT 与多 SKU 扩展绑定，不单独引入。

### 3.6 暂缓与不引入

| 技术 | 决定 | 理由 | 复议条件 |
|---|---|---|---|
| A2UI | 暂缓 | 前置的流程执行器未做；协议版本在变 | 现有计划 Task 9 验收后 |
| OpenTelemetry GenAI 规范 | 不引入 | 规范未稳定；现有 `CallRecord` 已满足评分需要 | 规范发布稳定版，且需要对接外部观测平台 |
| Mem0、Zep、Letta 等记忆框架 | 不引入 | 经营数据已结构化存于 PostgreSQL；再加一套存储会带来第二个事实来源 | 出现大量非结构化长期对话记忆需求 |
| 通用语义压缩 | 不引入 | 尚无证据表明当前任务因上下文过长而失败 | X1 实测出现因超预算导致的失败 |
| LLM 协调器 | 不引入 | 路由规则应先有对照证据，见第 5.7 节 | 按需策略在复杂用例上显著优于单 Agent，且规则路由成为瓶颈 |
| 强化学习检索、自修改代码或评测器 | 不引入 | 没有可靠奖励和样本量；自修改评测器会破坏整套门槛 | 不复议自修改评测器 |

## 4. 总体设计

### 4.1 自进化阶梯

每一级只在下一级的评测可信之后才打开。

| 级别 | 演化对象 | 手段 | 状态 |
|---|---|---|---|
| L0 观测 | 无 | 调用账本、评分轨迹 | 已有 |
| L1 提示词 | 专家提问与角色指引 | GEPA，离线 | X2 |
| L2 Skill 文本 | 基线 Skill 的摘要、步骤、例外 | GEPA，离线 | X3 |
| L3 流程与路由 | 受限流程图、路由规则 | 现有计划 Task 9–10；路由规则来自对照实验 | X5 |
| L4 评测器、记忆架构、代码 | — | 不做 | — |

### 4.2 数据流

```mermaid
flowchart LR
    C[用例与 oracle] --> R[隔离运行器]
    B[文本制品 当前版本] --> R
    R --> T[评分轨迹]
    T --> S[评分器与说法核对器]
    S --> F[分数与文字反馈]
    F --> G[GEPA]
    G --> N[候选文本制品]
    N --> R
    N --> D{发布门槛}
    D -- 通过 --> P[入库并由配置启用]
    D -- 未通过 --> X[保留现版本并记录]
```

优化器只接触训练和验证两个划分；发布门槛使用它从未见过的划分。

### 4.3 不变量

- 优化对象只有文本制品里标为可演化的组件。安全指令、输出格式、工具清单、角色工具白名单、评分器、金标、业务规则都不可演化。
- 候选只能离线产生。线上进程不安装优化器，不发起优化。
- 启用和回滚都是一次配置变更，运行记录里冻结所用版本的哈希。
- 运行自身的账本不能证明任务成功；经营事实只来自可信 oracle。
- 未知用量和未知成本不记为零；未判定不算通过。

## 5. 评测底座（X1）

### 5.1 文本制品

把现在写死的提示词收进一个带版本的制品，放在 `agent/src/shopsteward_agent/cases/bundles/case-experts/` 下，每个版本一个 JSON 文件，初始版本 `seed` 的内容与现有文本逐字相同。

| 字段 | 含义 |
|---|---|
| `bundle_id`、`revision`、`parent_revision` | 制品标识与血缘 |
| `components` | 组件名到文本的映射 |
| `content_hash` | 组件内容的 SHA-256 |
| `provenance` | 来源：人工，或优化器名称、版本、种子、评测次数预算、训练与验证集哈希、任务模型与反思模型的配置哈希 |
| `gate` | 发布门槛报告的引用；`seed` 为空 |

可演化组件六个：`question.evidence`、`question.impact`、`question.options`，以及三个初始为空的 `guidance.*`。单 Agent 和固定流程使用的提问继续由三条专家提问按固定规则拼出，不单独存放。这样无论文本怎么演化，四种策略被问的始终是同一组问题，策略对照保持公平。

启用方式是新增配置 `AGENT_CASE_TEXT_BUNDLE`，默认 `seed`。加载时校验哈希。运行结果里的 `routing.prompt_hash` 改为记录制品的 `content_hash`，并新增 `routing.bundle_revision`。

### 5.2 把冻结证据工具下沉到 agent 包

专家用的只读工具和路由信号现在定义在后端的 `analyze_case_experts` 里。离线运行器如果另写一份，两处会走样。因此把这部分移到 `agent/src/shopsteward_agent/cases/frozen.py`，提供两个函数：由快照和方案构造只读工具，以及由快照和方案计算路由信号。后端只保留模型配置、持久化和权限复核；离线运行器调用同一份实现。

### 5.3 用例集

用例由参数化模板生成，oracle 是确定性求解器 [`solve`](../../../backend/app/planning/recovery/solver.py) 对同一输入的输出。求解器本身的正确性由后端已有的手算金标测试锚定，所以这里衡量的是解释是否忠于求解结果，不是求解器的质量。

首批覆盖只需结构化输入的场景族：延迟造成时间缺口、总量够但中途断货、低价方案过晚、压低预算、原采购状态未知、部分到货、无需行动、起订量与整包与现金底线边界。依赖文档的场景族等文档类工具接入后再加。

划分按模板进行，一个模板只属于一个划分。

| 划分 | 用途 | 规模 | 谁能读 |
|---|---|---|---|
| smoke | 跑通流程，只用模拟模型 | 12 | 所有人 |
| evo-train | 优化器的反思小批 | 12 | 优化器，含文字反馈 |
| evo-val | 优化器的候选选择 | 12 | 优化器，只见分数 |
| gate | 发布门槛 | 不少于 24 | 只有门槛运行器；优化器永不接触 |
| OPS48 锁定集 | 研究结论 | 48 | 配置冻结之后，按 v1.2 第 19 节 |

evo-train 加 evo-val 就是 v1.2 所说的 24 个开发用例；gate 是本设计新增的。课程截止前至少完成前四个划分，共 60 例。只有这四个划分时，结论只能表述为开发级结果。

每个用例由三部分组成：现有 `CaseContract`；冻结的求解输入和求解输出；一组必须被说清的条件及其判定方式（第 5.4 节）。

### 5.4 可判定的结构化说法与优化用分数

专家输出的 `claims` 已支持可选的 `subject` 和 `applicability.result`。在固定的输出约定里补一张很小的词表，使一部分说法可以由代码对照求解结果判定：

| `subject.type` | `subject.id` | 允许的 `result` | 对照的求解结果 |
|---|---|---|---|
| `candidate` | 候选 ID | `recommended`、`feasible`、`rejected` | 推荐候选、各候选是否可行 |
| `gap` | 候选 ID | `none`、`day-N` | 该候选在七日内第一次出现丢失需求是第几天；没有则为 `none` |

首版只有这两类。新增类型必须由开发集上的具体失败来说明必要性。实现时把缺口的结果从“有或无”改成了“第几天开始”，因为旗舰场景要求指出缺货发生日，只答有无太容易。

同一对象上可以同时成立的结果不算专家分歧：推荐的候选必然也是可行的，所以 `recommended` 和 `feasible` 视为同一立场，只有它们与 `rejected` 才构成需要裁决的冲突。

新增一个可信的“说法核对器”，放在 `posttraining` 的 `case_eval` 里。它读合并后的说法和求解结果，产出观察项：与求解结果矛盾的说法数（期望为 0，属于关键失败）、必须条件是否全部覆盖、已覆盖条数。

优化器需要每个用例一个标量。定义如下：

- 运行未完成、有子任务失败、出现关键失败、或有任何说法与求解结果矛盾：0 分。
- 否则：必须条件的覆盖比例，取值 0 到 1。
- 第二目标：节省程度，等于 1 减去“实际模型调用数除以根预算”。

这个分数只供优化器给候选排序，**不作为质量成绩对外报告**。没有结构化标注的自由文字仍可能出错，所以发布门槛另外要求人工语义复核（第 6.4 节）。这是本设计里最可能在试跑后调整的部分，需要项目组确认。

### 5.5 批量运行器

新增 `posttraining/src/shopsteward_pt/strategy_eval/`，入口形如：

```powershell
python -m shopsteward_pt.strategy_eval run --cases <目录> --strategies fixed,single,static_multi,adaptive_multi --bundle seed --replicates 2 --profile <模型配置.json> --out <目录>
```

每次运行新建运行器、内存检查点和预算账本，不连接数据库、后端或供应商，因此不存在业务副作用。输出评分轨迹，再交给现有的 `case_eval` 评分和出报告。它需要 LangGraph，所以在主环境运行；`case_eval` 的评分部分保持只依赖 Pydantic。

约束：

- 提供模拟模型模式，供持续集成使用。
- 提供全局模型调用上限，发送前预留，超过即停止并保留已完成的结果。
- 价格未配置时成本为未知；只有在带版本的价格表存在时才计算金额。

规模估计：24 个开发用例、4 种策略、2 次重复，共 192 次运行。按每次运行 1 到 6 次模型调用估计，约 500 到 700 次调用。当前传给专家的快照和方案较大，集成测试需要把输入上限调到 48,000 才能放下。因此先用 10 个用例试跑，拿到实测的 token 和时延，再决定额度；如果输入规模成为成本主因，再考虑只向专家投影部分候选。

### 5.6 MAST 失败标签

标签只用于诊断，不参与任务成功的判定。能由代码判定的自动打标，其余由复核者标注，并记录来源。

| MAST 模式 | 判定方式 | 信号 |
|---|---|---|
| FM-1.1 违背任务要求 | 自动 | 只读意图下尝试写入；输出不符合固定格式 |
| FM-1.2 违背角色要求 | 自动 | 调用未提供给该角色的工具 |
| FM-1.3 步骤重复 | 自动 | 同一子任务内相同工具、相同参数重复调用 |
| FM-1.5 不知何时停止 | 自动 | 因模型、工具或时间预算耗尽而结束 |
| FM-2.2 该问不问 | 自动 | 用例要求澄清而没有提出 |
| FM-3.1 过早结束 | 自动 | 状态为完成但必须条件未覆盖 |
| FM-3.2 未核实或核实不全 | 自动 | 数字类说法未引用求解方案；分歧未被裁决 |
| FM-3.3 核实错误 | 自动 | 补查的裁决与求解结果矛盾 |
| FM-1.4、FM-2.3、FM-2.4、FM-2.6 | 复核 | 需要读轨迹判断 |
| FM-2.1 对话重置、FM-2.5 忽视其他 Agent 的输入 | 结构上不出现 | 专家之间不对话，合并由代码完成 |

### 5.7 预注册的策略对照

在看到任何真实结果之前写下假设和判定规则。

- 假设一：在只含结构化证据的恢复用例上，按需专家的任务成功不高于单 Agent，而模型调用更多。依据是规模化研究对顺序型任务的结论。
- 假设二：固定三专家不优于按需专家。
- 假设三：固定流程在简单用例上与其他策略相当。

判定规则沿用 v1.2：单 Agent 同样可靠且更便宜时，产品默认策略改为单 Agent。这意味着实验可能得出“不该默认用多 Agent”的结论，届时如实采用。

每个用例记录三个特征供事后分析：报价数、相互独立的子问题数、可用工具数。它们只用于解释结果，不提前写成路由规则。

文本版本是独立的实验因素。主对照统一使用 `seed`；演化后的文本另列，不能拿“演化文本的按需专家”去比“初始文本的单 Agent”。

## 6. GEPA 接入（X2）

### 6.1 环境与依赖

GEPA 装在单独的虚拟环境里，不进入 API、worker 和 `posttraining` 的评分环境。PyPI 当前版本为 0.1.4（2026-07-15 发布），要求 Python 3.10 到 3.14，MIT 许可，依赖中包含 LiteLLM。安装时锁定确切版本并检查依赖树。

### 6.2 适配器

实现 GEPA 的适配器协议，位置 `posttraining/src/shopsteward_pt/strategy_eval/gepa_adapter.py`。

| GEPA 概念 | 本项目对应 |
|---|---|
| 候选：组件名到文本的映射 | 文本制品的可演化组件 |
| 一条数据 | 一个 evo-train 或 evo-val 用例 |
| `evaluate(batch, candidate, capture_traces)` | 对每个用例用候选文本跑一次指定策略，评分，返回逐例分数、输出和轨迹；第二目标放进 `objective_scores` |
| `make_reflective_dataset(candidate, eval_batch, components_to_update)` | 对每个待更新组件，给出该角色看到的输入摘要、该角色的输出、未通过的检查及原因、MAST 标签和调用数 |

两条规则。单个用例失败时返回 0 分和原因，不抛异常，这是协议的要求。文字反馈只在训练划分上生成；验证划分只回传分数，避免金标通过反馈泄漏给优化器。

### 6.3 模型与预算

任务模型用与对照实验相同的冻结配置。反思模型用更强的模型。首选让反思调用走我们自己的模型客户端，这样密钥文件、超时和用量记录保持一致；GEPA 是否接受自定义的可调用对象作为反思模型，要在装好的版本上核对，不支持时改用 LiteLLM 指向同一端点。

试点预算：评测次数上限 150。一次评测是一个用例的一次策略运行，约 2 到 4 次模型调用，所以任务调用不超过约 600 次，另加几十次反思调用。先演化产品默认的按需策略所用的三条专家提问，其余组件不动。预算允许时跑两个优化器种子，分别报告。

### 6.4 产物与发布门槛

优化器的输出是一个新的文本制品版本，`provenance` 里记下全部配置。它必须通过以下四条才能入库启用，全部在 gate 划分上、与 `seed` 配对、每个用例至少两次重复：

1. 零关键失败，零与求解结果矛盾的说法。
2. 没有观察到退化：不存在 `seed` 多数重复成功而候选多数重复失败的用例。
3. 达到事先写下的改进目标，例如必须条件覆盖率提高 10 个百分点，或同等成功下模型调用减少 15%。目标在优化开始前定下，之后不换。
4. 两名成员独立复核不少于 12 个用例的自由文字，证据适用性和交付清晰度没有变差；分歧按现有规则保持待裁决。

报告写明用例数和区间，并明确这不是统计意义上的非劣证明，原因见第 7.6 节的算术。文本制品是开发者发布的全局内容，启用和回滚都只是改配置，风险低于按用户自动启用的 Skill，所以用这套较轻但不含糊的门槛。

### 6.5 安全边界

- 演化出的文本进入用户角色的消息和上下文数据，不进入系统指令。
- 候选入库前做静态检查，出现要求批准采购、跳过确认、忽略约束之类的指令即拒绝。
- 专家只有只读工具，最坏结果是解释有误，由门槛拦截。
- 反思模型看到的是训练划分的合成用例，不含任何用户数据。

### 6.6 停止条件

两个种子都没有产生通过门槛的版本时，保留 `seed`，把过程和结果写成负面结论，不扩大到更多组件。通过门槛但对照实验显示单 Agent 更优时，演化对象改为单 Agent 所用的文本。

## 7. Skill：基线制品与修订（X3）

### 7.1 现有路径的问题

[extractor.py](../../../agent/src/shopsteward_agent/learning/extractor.py) 用两次模型调用从轨迹直接写出候选。它有结构校验，但没有执行验证；候选要启用还缺回放执行函数；每批最多三次模型调用的预算也容不下任何基于执行的修订。

### 7.2 基线 Skill 作为产品内容

新增目录 `agent/skills/<名称>/`，每个基线 Skill 两个文件：`skill.json` 是权威的 `SkillSpec` 加来源信息，`SKILL.md` 由它生成。首批两个：`supply-delay-recovery` 和 `cash-constrained-replenishment`，对应已有的两个任务族。

基线 Skill 不含个人数据，不需要学习同意，用独立开关 `AGENT_BASELINE_SKILLS_ENABLED` 控制，默认关闭。它与按用户学到的 Skill 共用现有的注入上限（最多 3 条、1800 字节）和适用性判断。冲突时的优先级是：用户当前约束、用户明确保存的偏好、按用户学到的 Skill、基线 Skill。用户可以在学习页停用某个基线 Skill。

基线 Skill 的发布门槛与文本制品相同（第 6.4 节），但用例是 Mission 级的。

### 7.3 Mission 沙箱运行器

Skill 指导的是 Mission Agent，它使用真实业务工具，所以第 5 节的冻结证据运行器不够用。新增 Mission 沙箱运行器：复用 [fixtures.py](../../../posttraining/src/shopsteward_pt/eval/fixtures.py) 里“每个用例一个全新隔离业务环境、真实进程内工具请求”的做法，把其中的受限五动作策略换成完整的运行时。它需要隔离的 PostgreSQL。

这个运行器同时解决三件事：它就是 `replay_suite` 缺的执行函数；它是 v1.2 上下文实验（CE 套件）需要的运行器；它产出带业务状态观察的评分轨迹，比如方案版本是否被改动。它是 X3 的主要工作量。

### 7.4 用 GEPA 修订 Skill 文本

可演化的只有三个文本字段：摘要、步骤、例外。任务族、输入、输出、前置条件、排除条件、所需工具是结构化字段，不交给文本变异。每个候选先过现有的 `validate_candidate` 和 `SkillSpec` 的长度限制，不合格直接 0 分。

反思模型除了训练反馈，还拿到一份固定的修复原则清单，例如“把写死的对象 ID 换成输入参数”“缺前置检查时在计算之前补上”。清单有版本，不参与演化。

### 7.5 按用户提炼路径的新定位

`extract_candidates` 保留。它的产物仍是草稿，仍要通过现有的完整门槛才能启用，默认不自动启用。它的作用变成两条：在“已学到的做法”页面向用户呈现观察到的模式；把重复出现的纠正作为线索，供维护者写进基线 Skill 或修复原则清单。不对单个用户运行 GEPA，现有每批三次调用的预算与一次优化需要的上百次评测不在一个量级。

### 7.6 需要确认：现有准入门槛的算术

[quality.py](../../../backend/app/learning/quality.py) 要求配对成功率差值的保守下界不低于 −2 个百分点。按代码里的 Wilson 区间计算：

| 配对用例数 | 候选与基线完全等同时的下界 | 零退化时通过所需的最少净改善例数 |
|---|---|---|
| 20 | −16.1 个百分点 | 6 |
| 24 | −13.8 个百分点 | 6 |
| 48 | −7.4 个百分点 | 6 |

一个与基线表现完全相同的候选，需要 189 个配对用例才能通过这一条。也就是说，按现有门槛，在几十个用例的规模上，只有效果很大的 Skill 才可能启用。这个门槛本身是诚实的，但它与“先交付一个可用的 Skill 闭环”的目标冲突。

三个选项：

- 甲：维持不变。结果是相当长时间内没有 Skill 被启用。
- 乙：分两档。自动启用（assist 模式）保持现有门槛；用户手动启用（suggest 模式）和基线 Skill 采用第 6.4 节的四条，并在界面标明“证据有限”。
- 丙：把门槛用例集扩到 189 例以上。

建议选乙。Skill 是注入上下文的建议文本，金额、权限和采购确认由业务层独立把关，手动启用加明确标注的风险可以接受。这一条放宽了发布门槛，在项目组确认之前不改代码。

### 7.7 Agent Skills 导出

| `SKILL.md` 部分 | 来源 |
|---|---|
| `name` | 任务族与标题生成的小写连字符名称，不超过 64 字符，与目录同名 |
| `description` | 摘要加“何时使用”，不超过 1024 字符 |
| `metadata` | 字符串键值：资产 ID、版本、内容哈希、评估报告 ID、Rubric 版本、来源域 |
| 正文 | 输入、前置条件、步骤、输出、例外、禁止事项 |

导出器自己校验这些约束，测试里再用规范提供的 `skills-ref validate` 复核一次，运行时不依赖该工具。按用户学到的 Skill 只在用户主动下载时导出。不支持导入外部 `SKILL.md`：外部文本不可信，要支持的话也只能作为草稿进入完整门槛。

## 8. 多 SKU 联合备货与 CP-SAT（X4，有条件）

触发条件：项目组决定做 v1.2 第 21.1 节的多 SKU 扩展，并且 SKU 数量超过 3 个或需要跨 SKU 的供应商约束。不满足时用枚举，不引入求解器。

设计要点：

- 每个 SKU 的候选仍由现有的逐日求解器生成，候选的支出和丢失需求是已知常数。
- 组合选择建模为每个 SKU 恰好选一个候选（含“等待”），约束是总支出不超过预算、采购后现金不低于底线。
- 目标分两级：先最小化重点 SKU 按优先级加权的丢失需求，再最小化支出。用两次求解实现，不用人为权重把两级混在一起。
- 在不超过 216 种组合的用例上，求解结果必须与枚举逐例一致，作为回归测试。
- 采用组合后的串行审批、部分执行状态沿用 v1.2 的规定，不因引入求解器而改变。

这一项直接对应课程的经营资源优化技术组；具体归类仍以课程口径为准。

## 9. 阶段路线与验收

估算按一位熟悉项目的工程师全时计算，不含人工复核、模型额度申请和等待。

| 阶段 | 交付 | 验收 | 估算 |
|---|---|---|---|
| X0 | 四种协作策略、代码合并、评分轨迹导出 | 已完成，见运行手册 | — |
| X1 评测底座（2026-10-08 已完成） | 文本制品与注入；冻结证据工具下沉；60 个用例的生成器；说法核对器；批量运行器；MAST 自动标签 | 模拟模型下全流程进入持续集成；真实模型 10 例试跑给出 token 与时延实测；开发集上四种策略、两次重复的对照报告 | 3–4 人日 |
| X2 GEPA 试点（2026-10-08 已完成一次） | 独立环境；适配器；一到两次优化；门槛报告 | 候选通过第 6.4 节四条并启用，或写出负面结论 | 2–3 人日，另需额度 |

课程截止前建议只承诺 X1 和 X2。X3 里“两个基线 Skill 加导出”约 1.5 人日，可以作为展示内容先做，但没有 Mission 沙箱运行器就不能声称它们通过了门槛。

## 10. 风险

| 风险 | 应对 |
|---|---|
| 优化用分数与真实质量脱节，优化器学会堆砌结构化说法 | 矛盾即 0 分；门槛含人工语义复核；分数不对外报告 |
| 用例少，优化器过拟合 | 按模板划分；门槛划分对优化器不可见；至少两个种子 |
| 评测噪声被当成改进 | 每例至少两次重复；报告区间和原始计数 |
| 输入过大导致成本超预期 | 先做 10 例试跑；全局调用上限；必要时投影候选 |
| 实验显示多 Agent 没有优势 | 如实采用单 Agent 为默认；多 Agent 的适用边界作为结论报告 |
| 用求解器当 oracle，掩盖求解器自身的错误 | 求解器由独立的手算金标测试锚定；报告中说明衡量的是解释忠实度 |
| GEPA 版本尚处 0.1.x，接口可能变化 | 锁定版本；适配器是唯一接触点；接口核对列为 X2 第一步 |
| 课程截止前时间不足 | 只承诺 X1 和 X2；其余明确标为后续 |

## 11. 与现有设计的关系

- 对统一设计 v1.2：实验部分新增 gate 划分和“文本版本”这一实验因素；产品默认策略可能依据对照结果改变。其余不变。
- 对自进化总设计及其实施计划：Task 4 的从零提炼保留但降为辅助路径；Task 7 缺的回放执行函数由 Mission 沙箱运行器提供；计划中的 `evolution_eval` 评测模块由 `strategy_eval` 和已有的 `case_eval` 承担；Task 9 到 12 不变，顺序排在 X3 之后；A2UI 的目标版本在启动时重新核对。
- 不变的部分：业务硬规则、人工采购确认、`memory_edit` 的显式语义、学习同意与数据隔离、现有 Skill 生命周期。
