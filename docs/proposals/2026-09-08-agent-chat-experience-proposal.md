# ShopSteward 聊天渲染与 Agent 执行可视化修改提案

日期：2026-09-08　｜　面向：前端、Agent / 后端、组内演示负责人　｜　状态：供评审与排期

建议把聊天区升级为一个能看见「正在做什么、依据来自哪里、什么发生了变化」的备货助手。保留现有浅蓝、玻璃卡片和业务工作台，在其中加入富文本回答、执行状态条、文档证据卡和业务区域联动。

本提案依据当前工作区代码、仓库内已有桌面截图，以及指定 BAU Management Platform 中的 AI Assistant 源码。截图为已有验证产物，未在本次重新运行应用；接口结论以当前源码为准。本文是设计与协作提案，不代表相关功能已实现，示例中的数量与文案均为交互说明。

## 1. 当前缺口与可复用基础

| 现状 | 对体验的影响 | 修改方向 |
| --- | --- | --- |
| `AgentConversation.vue` 使用 `{{ m.content }}` 输出助手回答 | Markdown 的 `**`、列表和表格直接暴露；信息难扫读 | 专门的 Markdown 消息组件 |
| `.chat-thread` 最大高度为 310px | 长回答与表格挤在小窗口内 | 提高默认可读空间，并提供展开对话 |
| 每 2.5 秒重新读取会话、消息和最新 run | 已有轮询基础，但没有消息增量合并与细粒度执行展示 | 提取会话状态层，增量更新消息与工具记录 |
| 界面只区分等待、正在处理、等待补充、失败 | Agent 检索和调用工具时看起来都像卡住 | 当前状态 + 可展开的执行步骤 |
| `RunView.tools` 已返回工具记录，前端未渲染 | 用户看不到 Agent 实际调用过什么 | 首期直接接入已完成步骤 |
| `MessageView.references` 已有业务与文档引用，前端未渲染 | 回答的依据不可点击核验 | 引用列表、版本信息、证据抽屉 |
| Agent 可试算、修订方案、记忆偏好；现有采购有单独确认流程 | 容易把“方案变了”理解成“已经买了” | 将试算、方案修订、实际执行分别展示 |

**接口边界必须先对齐：** 当前 `GET /api/v1/agent-runs/{run_id}` 的每条工具摘要实际只包含 `tool`、`invocation_id`、`ok`、`references`。记录在工具得到结果后写入；没有开始事件、执行中状态、耗时、原始参数或完整结果。`RunView.output` 也不是已约定的前端图表 / diff 协议。

因此，首期可以真实展示“已读取经营数据”“文档检索已完成”，不能只凭 `RUNNING` 展示“正在读合同第三页”。真正的实时工具灯效需要后端补充生命周期事件。

## 2. 推荐方向：聊天里的执行条，与页面上的依据联动

| 方案 | 内容 | 取舍 |
| --- | --- | --- |
| **A：聊天增强 + 业务联动（推荐）** | 富文本、紧凑执行条、按需展开步骤、证据抽屉、现有卡片高亮 | 最适合当前备货工作台，可分期上线 |
| B：独立全屏 AI 工作台 | 类似 BAU 的左聊天、右成果区域，提供独立入口 | 适合长时间文档工作，但需新增页面结构和导航，当前收益较低 |
| C：常驻 Agent 节点图 | 全屏节点、连线、实时执行轨迹 | 展示感强，但抢占经营信息空间；可留作后续演示专用视图 |

推荐 A。桌面保留中间备货卡片和右侧「店铺此刻」，点击来源时再打开证据抽屉；空间不足时抽屉覆盖背景栏，避免挤出第三列。移动端变为全屏证据面板，并保留返回时的聊天位置。

## 3. 消息渲染：先解决可读性

### 3.1 回答正文

新增 `MarkdownMessage.vue`，支持段落、标题、粗体、列表、引用、链接、代码块和表格。助手正文以浅色阅读面为主，用户消息保留右对齐气泡；长回答不必包进高饱和度蓝色大气泡。

- 正文 14–15px，行高约 1.7；段落间距 10–12px，正文左对齐。
- 表格使用独立横向滚动容器，不能撑宽页面；金额右对齐，单位写在表头。
- 回答末尾提供「复制回答」；代码块单独复制。图表 / CSV 导出放在后续增强中。
- 用户消息仍作为普通文本显示。模型输出不得创建 Vue 组件、执行脚本或插入可提交的业务表单。
- 首期保留整段回答到达后的淡入。逐字流式需要真实增量接口，不将整段答案拆字后伪装成模型仍在生成。

可以参考 BAU 的 `markdown.ts`，使用 Markdown 解析与 HTML 清理两个独立环节；建议关闭原始 HTML，链接仅允许产品认可的协议，清理后不再拼接不可信 HTML。Markdown 扩展能力与清理配置参见 [markdown-it 官方文档](https://markdown-it.github.io/markdown-it/) 和 [DOMPurify 官方说明](https://github.com/cure53/DOMPurify)。Nuxt 接入时明确服务端渲染策略：首期可在服务端输出转义纯文本，客户端挂载后完成富文本渲染；需要 SSR 富文本时再提供经过验证的同构清理实现，不能直接在服务端引用浏览器 `window`。

### 3.2 输入与滚动

- 单行 input 改为自适应 textarea，最多展开 5 行；Enter 发送、Shift+Enter 换行，中文输入法组合期间不触发发送。
- 发送后立即显示本地待确认用户消息，收到 `message_id` 后替换，避免等待下一次轮询才出现。发送失败保留内容和明确状态。
- 创建同一次发送时保存幂等键，结果不明时先核对或复用该键重试；不能每次重试都新建键导致重复消息。
- 仅在用户接近底部时自动跟随；用户向上阅读后显示「有新内容 · 回到底部」。打开引用不改变主聊天滚动位置。
- 桌面聊天默认高度建议约 420–560px，并提供展开至约 70dvh；窄屏控制嵌套滚动，输入区避开软键盘与安全区。
- `WAITING_INPUT` 显示独立补充信息卡，继续复用现有 `interrupt_id` 与 `/resume`。后台主动解读标注「经营变化更新」，不伪装成用户刚发起的请求。

## 4. Agent 状态与动效：让每一种亮起都有含义

### 4.1 执行状态条

状态条只占一至两行，默认展示当前阶段、简短说明和停止按钮。其下的能力标签是「业务数据 / 文档依据 / 方案试算 / 方案更新」，按本轮实际使用的能力出现，不是强制每轮都走完的进度条。

| 状态 | 显示文案 | 视觉处理 |
| --- | --- | --- |
| 本地请求未受理 | 正在发送… | 小圆点静态或轻动效 |
| `QUEUED` | 已收到，等待处理 | 灰蓝圆点，不显示虚构队列位置 |
| `RUNNING`，无细粒度事件 | 正在处理你的问题… | 主状态环轻微呼吸 |
| 有模型阶段事件 | 正在分析问题 / 正在整理回答 | 主状态环活动，工具标签不假亮 |
| 有工具开始事件 | 正在读取经营数据 / 正在检索文档 | 对应图标、步骤与页面区域活动 |
| `WAITING_INPUT` | 需要你补充一项信息 | 琥珀色问号，停止处理动画 |
| `SUCCEEDED` | 回答已完成 · 已执行 N 步 | 收起步骤为摘要；失败子步骤仍保留提示 |
| `FAILED` | 本轮未完成，可查看原因 | 错误标识与中文原因，已完成步骤仍可查看 |
| `CANCELLED` | 本轮已停止 | 静态终态；业务变更以真实记录为准 |

界面中的“思考中”指可公开的工作阶段，例如分析问题、等待工具、整理回答。不要编写模型的内心独白，也不要把内部推理内容当作要展示的数据字段。

### 4.2 工具与区域的映射

| 当前真实工具 | 面向用户的名称 | 联动对象与完成效果 |
| --- | --- | --- |
| `get_mission`、`get_plan` | 读取任务 / 当前方案 | 当前方案卡描边，完成后显示「已读取」 |
| `get_dashboard` | 核对现金、库存与在途 | 「店铺此刻」整个卡片亮起；没有更细数据时不猜测只读了其中某一格 |
| `read_sales_summary`、`read_timeline`、`read_experiences`、`get_action` | 查看销量 / 经营记录 / 历史经验 / 采购状态 | 对应来源标签亮起；无可见区域时仅亮步骤卡 |
| `search_documents` | 检索文档依据 | 文档图标活动；返回后列出实际检索所得来源 |
| `read_document_evidence` | 展开证据片段 | 对已知文档卡描边，证据面板已打开时才高亮对应片段 |
| `evaluate_plan` | 试算另一种采购安排 | 展示独立试算结果，标注「仅试算」 |
| `revise_plan` | 更新本轮待确认方案 | 新版本取得后显示数量 / 预计支出的前后对照 |
| `memory_edit` | 保存 / 修改偏好 | 成功后展示偏好回执；无操作细节时用「偏好已更新」 |
| `request_check` | 请求重新检查 | 首先显示「已提交检查请求」，待业务新结果出现后再提示方案更新 |

未知工具采用通用「执行步骤」样式并保留可展开的工具名称；前端不能根据名字含 `update` 等字符串就判定其会写入数据。

**首期灯效：** 轮询首次发现一条成功工具记录，相关区域闪亮一次约 800ms，并标注「刚刚读取完成」；失败显示失败。初次打开历史、刷新恢复、重复轮询均不重播。首期无法测得工具执行耗时。

**实时灯效：** 收到 `tool.started` 后，该步骤呼吸；`tool.completed` 后变为完成标记，`tool.failed` 后变为错误标记。工具结束后主 run 可能继续执行，不能将一个工具完成当作整轮完成。

### 4.3 动效规格

- 延续现有 `--blue: #286bc1` 与浅灰蓝背景。读取使用蓝色；成功使用绿色勾号；待输入 / 结果待核实使用琥珀色；失败使用红色图标和文字。
- 卡片入场 160–220ms，位移不超过 4px；读取呼吸约 1.6s 一周期；依靠淡色边框 / 背景完成，避免全屏闪光。
- 可见区域最多两个持续动画焦点：当前步骤和其目标卡片。即使工具并行，也以静态计数概括其他活动步骤。
- 不使用虚构百分比或倒计时。耗时很长时显示「仍在处理」及停止入口；连接过期时显示「连接中断，正在同步」，不维持一个看似正常的读取动画。
- 支持 `prefers-reduced-motion`：去掉循环和位移，用图标、文字与描边表达状态。颜色不作为唯一识别方式。
- 不因自动读取而打开抽屉、滚动页面或抢键盘焦点；用户点击步骤 / 来源后才定位目标。

## 5. RAG 证据卡：从“搜过了”到“能核验”

RAG 展示分为三个层级，避免把检索候选都称为最终回答的逐句依据。

1. **执行层：** “正在检索文档”或“文档检索完成”。计数来自实际引用，明确写「文档数」或「片段数」，不混用。
2. **来源层：** 「本轮获取的来源」，显示资料标题、文档版本、段落 / 章节 / 页码。现有 references 是累计获得的引用，尚不能证明每一个片段都支持某一句结论。
3. **核验层：** 点击来源打开证据抽屉，展示原文片段与定位，并提供对应版本的原件入口。若后续增加句子与引用的结构化关联，才在正文旁生成精确 `[1]` 标记。

文档引用身份至少保留 `id + version_id + generation_id + chunk_id + metadata_revision`，并保留返回的哈希和 `locator`。不能仅按标题合并，也不能在查看历史回答时悄悄替换为最新版本。

现有文档 references 含版本和定位，但不直接包含标题 / 原文片段。文档详情与版本接口可用于补充基础信息；缺少页码时展示真实章节或段落，不能显示“第 0 页”。未解析到标题时先显示「文档来源」，再按需加载标题。

当前原件下载接口为 `GET /api/v1/documents/{document_id}/versions/{version_id}/content`。前端需确认生成路由白名单已包含它，并配置能保留二进制内容、MIME 和下载文件名的同源下载代理；现有 JSON 代理不能直接视为已验证的下载通路。预览 / 原件下载仍须走当前身份权限，前端不要直接调用内部 Agent 工具端点。

**需要后端补充的部分：** 面向用户的证据展示 DTO / 读取端点，返回已授权的 `title、excerpt、locator、版本信息、可用性`；引用过期、撤回、权限变化或原件不可用时，展示明确状态并保留历史定位。完整原文预览不列入纯前端首期承诺。

## 6. 动态结果组件：把结果放到适合的容器

| 组件 | 展示内容 | 数据条件 |
| --- | --- | --- |
| `SourceChip` / `EvidenceDrawer` | 来源、版本、定位、证据 | 引用已有；全文片段需展示接口 |
| `PlanComparisonCard` | 不同数量对应的预计缺货、支出、采购后现金 | 当前方案可用已有 candidates；单次 Agent 试算需补充结构化结果 |
| `ChangeReceiptCard` | 字段旧值 → 新值、作用范围、版本、状态 | 当前方案刷新可展示新版；准确历史 diff 需可核验前后快照 |
| `ClarificationCard` | 问题、补充输入、停止本轮 | 已有 `question` / `interrupt_id`；选项按钮需新增明确 options 字段 |
| `CheckReceiptCard` | 检查已受理、等待业务结果、查看新方案 | 请求回执与业务结果要分别关联 |

结构化组件使用白名单与确定的 schema 注册。模型文本里的“20 件”“¥200”不通过正则提取后变成可操作业务数据；金额复用现有 `money()` 按分转换，缺失值显示「未取得」，不当成零。

### 必须分开的三种变化

**只试算：** 用户问「如果只买 20 件呢？」时，显示带「仅试算」标签的对比卡。当前方案与现金 / 库存保持原有事实，页面最多高亮试算结果区域。

**方案修订：** 用户明确要求「将本轮上限改成 20 件」后，`revise_plan` 成功并取得新方案版本，才显示「待确认方案已更新：40 → 20 件」。真实现金仍未扣减，按钮为「查看待确认方案 / 核对采购」，复用已有确认流程。

**实际采购：** 用户完成现有采购确认后，按业务 action 状态更新「已受理 / 结果待核实 / 未成功」；读取新的经营快照后再更新并高亮现金与在途。采购受理与实际到货分别呈现，不能提前点亮“已到货”。

停止 Agent 只停止本轮后续工作，不能承诺撤销已经提交的方案修订或其他业务变更。回答失败也不意味着此前所有工具都未产生效果；回执必须以实际业务状态为依据。

## 7. 前后端分工与事件契约建议

### 7.1 第一阶段：沿用现有轮询

新增 `useAgentConversation` 管理消息、run、工具记录、引用与请求状态；`AgentConversation.vue` 负责组装视图。状态以当前身份 / 门店 / 任务 / 会话为作用域，避免将聊天状态存为跨店铺无区分的全局单例。

- 首次加载读取历史；之后使用已有 `after_seq` 追加消息，以消息 id 去重。上拉历史采用单独分页，不再固定每次最多遍历 10 页就停止。
- 工具记录以 `(run_id, invocation_id)` 去重；同名工具可调用多次，不能像简单的“按名称找第一个未完成工具”那样配对。
- 消息按 `run_id` 归属执行步骤。老回答展开过程时按需读取对应 run，不能把最新 run 的步骤挂到所有回答下。
- run 结束后完成最后一次消息同步，再降低轮询频率；开启主动解读的会话仍需低频发现新 run。页面隐藏时降低频率，恢复可见立即同步。
- 任务切换、门店切换、退出登录时中止请求 / 连接并递增作用域版本，丢弃旧作用域晚到响应；保留当前代码已有的版本隔离思想。
- 避免聊天组件在不同业务卡片间重新挂载时丢失输入、重复启动计时器或重播历史动画。

### 7.2 第二阶段：增加可回放的进度事件

建议新增 `GET /api/v1/agent-runs/{run_id}/events?after_seq=N`，用 SSE 发送事件；保留 run 快照作为恢复与降级依据。消息提交继续走现有 POST，事件流负责订阅已受理 run 的执行过程。以下字段与端点均为提议，当前未实现。

```json
{
  "schema_version": 1,
  "event_id": "evt-example-12",
  "run_id": "run-example",
  "seq": 12,
  "at": "2026-09-08T09:00:00Z",
  "type": "tool.started",
  "invocation_id": "invocation-example",
  "payload": {
    "tool": "read_document_evidence",
    "label": "正在展开供货条款",
    "operation": "read",
    "targets": [{ "kind": "document", "id": "doc-example" }]
  }
}
```

| 事件 | 最小业务含义 / 额外数据 |
| --- | --- |
| `run.started` | 开始执行 |
| `phase.changed` | 有限枚举 `analyzing / composing`，只表达公开阶段 |
| `tool.started` | 稳定 invocation id、工具名、操作类别、已知目标 |
| `tool.completed` / `tool.failed` | 同一 invocation id、真实起止时间、脱敏摘要、引用或中文错误 |
| `artifact.ready` | artifact id、允许的 kind、schema version、可核验数据 / 来源；首批仅支持试算与变更回执 |
| `input.required` | 问题与 interrupt id；可选结构化选项 |
| `run.completed` / `run.failed` / `run.cancelled` | run 终态，随后同步持久消息与业务快照 |
| `message.delta`（后续可选） | message id 与文本增量；持久最终消息作为最终一致内容 |

服务端须在工具真正开始时提供事件，在业务提交成功后才发送完成与变更回执。数据库事务回滚不能遗留“保存成功”的事件；可以采用与业务提交一致的事件持久化机制。重试需明确是同一调用的重放还是新一次尝试，不能重复写入业务。

SSE 帧提供 `id`，重连使用客户端已处理的游标；忽略重复事件，检测序号缺口并补拉，快照与事件游标需建立一致恢复点。流结束但没有终态事件时查询 run，不能直接判成功；游标超出保留期时退回快照，并提示过程记录不完整。SSE 的事件命名、重连与 `id` 机制参见 [MDN 官方技术文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

**本项目的接入阻点：** Nuxt 的 `frontend/server/api/backend/[...path].ts` 目前通过 `$fetch.raw` 获取结果，超时 20 秒，再返回 `response._data`，并受自动生成的路由白名单约束。新增 SSE 要同时新增端点契约、重新生成类型 / 路由白名单，以及实现不会缓冲整段响应的流式代理，转发重连游标，处理心跳、客户端断开与凭据失效；不能仅在聊天组件里加 EventSource 就算完成。

浏览器沿用现有同源服务端身份代理，不暴露内部 Agent token。SSE 无法建立时退回第一阶段轮询，明确显示“进度同步中”。流式文字不是展示工具进度的前置条件，可晚于工具事件交付。

### 7.3 前端组件建议

```text
AgentConversation
  ├─ AgentMessage
  │    ├─ MarkdownMessage
  │    ├─ AgentRunStatus + ToolTimeline
  │    ├─ SourceChip[]
  │    └─ AgentArtifact → PlanComparisonCard / ChangeReceiptCard
  ├─ ClarificationCard
  └─ AgentComposer

页面共享：EvidenceDrawer + AgentActivityTarget
状态层：useAgentConversation + useAgentActivity
```

`useAgentActivity` 只提供“哪个业务实体正被访问 / 哪个版本刚更新”的显示状态，不直接修改业务数据。`BusinessFacts` 与 `DecisionCard` 根据目标身份订阅高亮；所有现金、库存和方案值仍由现有业务状态层提供。

## 10. 验收场景

| 场景 | 必须看到的结果 |
| --- | --- |
| 问“为什么推荐这个数量” | Markdown 正常；`get_plan` 记录出现；来源可定位；没有虚构 RAG 步骤 |
| 问供货文档条款 | 有真实检索记录；P1 可见读取活动与对应文档；引用显示真实版本与定位 |
| 文档检索为空 / 失败 | 分别显示“未找到相关依据”和“读取失败”，不生成假文档卡 |
| 连续两次调用同一个检索工具 | 分别对应两个 invocation，不互相覆盖 |
| “如果只补20件，先只试算” | 仅试算结果；当前方案、库存、现金及采购数量不因展示而变化 |
| “明确修改本轮上限为20件” | 新待确认方案和可核验差异；现金不扣减；可进入既有核对流程 |
| 采购受理但结果待核实 | 对应业务状态，不提前显示“采购成功 / 已到货” |
| 等待补充、刷新后继续 | 问题恢复，输入提交到原 interrupt，而非新建重复任务 |
| 读取中取消、工具失败后结束 | 所有活动动画停止；已发生的变更仍可核对 |
| 断线恢复 / 重复事件 / 终态事件丢失 | 无重复消息和结果卡；补拉或快照恢复；不靠连接关闭判成功 |
| 切换店铺、任务、身份 | 旧响应不污染新会话，旧文档不在新作用域出现 |
| 查看历史、上滚阅读、长表格、窄屏、减少动效 | 不重播、不抢滚动、不撑宽页面、动画可关闭 |
| 非法链接 / HTML、引用撤回或无权访问 | 正文无执行能力，来源显示不可用状态 |

使用现有 Playwright 测试体系添加上述关键交互与事件回放场景；协议测试可用固定样例，不依赖每次真实调用模型。已有 `agent.spec.ts`、`agent-scope.spec.ts` 的只读试算、修订审批、恢复和隔离场景应保留并适配 DOM 改动。正式实施时运行 `typecheck`、`api:check`、构建及相关前端测试；真实模型端到端验证按现有 opt-in 方式执行。本次仅产出提案，未执行产品测试。
