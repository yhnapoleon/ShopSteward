## 1. 设计任务与已确认目标

用户要求先完整探索和深挖值得添加的用例，再形成完整设计；目标已确认是“课程旗舰＋技术研究兼顾”，并希望形成能够写入简历、经得起面试追问的经历。

本轮交付是用例决策和系统设计，不进行产品代码实现。用户没有要求每个候选都实现，也没有批准把所有未来能力并入首版。

据此，评价一个方向需要同时回答四个问题：

1. 店主完成了什么原来难以完成的事？
2. 哪些部分必须调查、解释或调整，哪些部分应该由代码计算？
3. 多 Agent 相比同等工具条件下的单 Agent，可能改善什么？什么结果会推翻这个假设？
4. 开发者能留下哪些个人贡献和可复现证据？

默认产品对象是使用合成经营环境的小型零售店主/运营者。课程演示不等于真实商家部署。求职方向按 AI Agent 应用与算法工程兼顾考虑；未假定个人独立完成团队已有全部模块。

上述约束使“经营异常应对”比“任意多部门自治商店”更适合作为下一步。

## 3. 用户真正需要委托的工作

### 3.1 用户不是缺少一份摘要

当店主收到供应商通知，他通常需要连续完成：识别通知与自己的关系、找到受影响订单、判断库存能否撑过缺口、寻找替代方案、确认现金是否允许、执行后追踪。

这些步骤由不同资料和状态支撑：文件能证明条款内容；业务库能证明当前库存和在途；预测描述未来需求假设；报价源约束实际采购。任何一个来源都不能包办全部结论。

### 3.2 工作成功的定义

用户能够明确选择“等待”“应急补购”“补充缺失条件”等下一步，并知道依据、代价和复查时点。若选购且条件齐备，应能生成后端可批准、可发送的计划。若执行条件不足，仍应交付已核实的影响和具体缺项。

“没有违规但没完成任何有用工作”不是成功；“生成流畅报告”也不足以代表解决问题。

## 4. 发散：八类候选

评分不用伪精确的加权总分。下表中的高/中/低是相对于现有项目的设计判断，不是用户调研结论。

| 候选 | 用户价值假设 | 多 Agent 适配 | 现有能力复用 | 新增负担 | 决策 |
|---|---|---|---|---|---|
| 通知变更→业务影响→补救方案 | 从读资料走向处理经营事件 | 高，存在跨来源、适用例外与动态追查 | 高 | 中 | 首版完整闭环 |
| 活动多 SKU 联合备货 | 在预算限制下分配库存保障 | 中高，候选调查可分解、预算必须集中求解 | 中 | 较高 | 第二阶段 |
| 缺货/积压复盘 | 区分预测、履约与决策问题 | 高，竞争假设与历史证据 | 中高 | 中 | 第三阶段/研究扩展 |

## 5. 深挖 A：供应变化影响与补救

### 5.1 典型委托

“供应商说这批货要晚到，看看哪些任务受影响，帮我保住接下来一周的供应，采购后现金至少保留 500 元。”

### 5.2 角色、输入和产物

用户是店主/运营者；供应商通知是资料，不因被上传就自动成为账本事实。已受理订单、实际库存和现有报价由结构化源提供。

系统交付一个持续事项：事件说明、受影响清单、时间轴、候选对比、可接受的计划及跟进记录。它不改变现有 Mission 的“持续补货委托”含义。

### 5.3 真正需要的协作

- 证据调查：通知是否针对这个 SKU/订单，旧订单是否豁免，哪份附件才包含实际条件？
- 经营影响：库存在哪个时间段不足，已确认在途何时能计入？
- 方案探索：现有候选是否覆盖缺口，是否值得补查新的供应条件？

证据专家可能指出“旧订单不受新起订量影响”；经营专家可能指出“周期总量足够但前三天断货”；方案专家可能发现“便宜方案到得太晚”。这些新发现会改变下一步，而不是固定执行三段摘要。

### 5.4 核心变体

| 变体 | 正确处理 | 不能采用的捷径 |
|---|---|---|
| 通知只影响未来订单 | 区分现有在途与新采购 | 一律延期所有订单 |
| 新旧通知冲突 | 核对对象、生效时间、来源；无法解决则保留分支 | 简单选择上传时间最新的文件 |
| 延迟后仍有足够现货 | 给出无需采购与复查时点 | 为展示 Agent 一定下单 |
| 便宜报价到货过晚 | 显示便宜但不能解决时间缺口 | 只比较单价和七日总量 |
| 最快报价起订量过高 | 计算资金和期末余货，再判断 | 自动降低起订量 |
| 只有部分订单受影响 | 按 action_id 和剩余量计算 | 用 SKU 总在途粗暴覆盖 |
| 原订单提交结果 UNKNOWN | 继续分析，但先核实原行动才可新提交 | 当作未下单再次采购 |
| 用户中途降低预算 | 更新目标版本，只重做依赖预算的结果 | 覆盖旧对话或沿用旧计划 |
| 通知撤回/货已提前到达 | 使旧影响失效，保留事件历史 | 删除证据和既有采购记录 |
| 所有替代方案无效 | 交付缺口与可选择条件，保留不买选项 | 凭空发明供应商 |

### 5.5 反例：什么时候不用多 Agent

只有一条结构化 ETA 修订、一个商品、一个既定采购选项时，确定性重算加单 Agent 解释已经足够。首版因此保留 simple 路径；复杂材料和需补查的场景进入协作路径。

### 5.6 最小有用范围

一个门店、一个目标 SKU、七日窗口、至多三个有效替代报价、最多一笔新应急采购；现有订单继续存在，不自动取消、退款、拆单或谈判。支持一份通知加少量关联文档、预算改口和一次事件重评估。

这一范围可以完成“收到通知→生成方案→批准→采购受理→到货/复查”的垂直闭环，仍具有足够的约束冲突来检验多 Agent。

## 6. 深挖 B：活动联合备货

### 6.1 典型委托

“下周活动重点卖三个商品，采购总预算 5000 元，优先保证主推商品，给我一套整体备货方案。”

成功意味着得到预算一致、到货时间一致的组合，而不是三个单品各自最优的建议。三个子 Agent 各自承诺预算会导致总量超支。

### 6.2 合理的分解

活动解释任务确定日期、商品和约束；商品分析任务按 SKU 构造候选档位；一个集中求解器处理共享预算、单供应商约束和服务目标；主 Agent 处理目标冲突及用户取舍。

纯数值预算分配不属于 LLM 的优势。若所有数据都已结构化、候选固定，多 Agent 相比单 Agent 可能没有明显价值。可检验的增益应来自活动资料理解、不同商品证据调查与选择性补查。

### 6.3 最容易遗漏的产品问题

1. 活动增幅不是已有 v6 预测的已验证能力。首版用用户确认的情景增幅，标注来源。
2. 普通销量未必等于潜在需求；缺货时实际销量受库存截断。
3. 没有售价、毛利与价格弹性数据时，不优化“利润”。用缺货量、重点商品保障和采购支出。
4. 一次联合选择不等于原子执行全部订单；当前门店执行链串行核实，需要逐步发布和批准子计划。
5. 第一笔采购改变现金，第二笔须重新校验。部分执行后停止，不能把整组标成“未执行”。

### 6.4 范围建议

三个 SKU、七日窗口、每 SKU 至多六个已验证候选、统一预算和显式优先级；最多 216 个组合，可以先枚举，不需要先上复杂优化框架。

这一阶段引入 `PortfolioProposal` 和按序执行记录；不修改一个 Mission 对应一个 SKU 的既有含义。每笔执行后重新评估剩余预算。商品替代、跨店调拨和促销价格优化另立设计。

## 7. 深挖 C：文档变更影响

“上传新的供应商通知，告诉我哪些正在进行的事需要处理。”

本用例不必独立变成另一套 Agent 系统。它是 A 的自然入口，也可以独立交付为第一片功能。

处理链：版本/原文读取→提取适用条件→关联商品/订单/方案→验证是否受影响→交付下一步。实体关联优先使用已有 supplier_ids、sku_ids 和结构化主键；模糊名称只生成候选，不直接决定业务写入。

成果不是“发生了三处变化”，而是“这两个待批准方案需要重算，这个已下单订单仍适用旧条款”。最难的测试应覆盖例外、跨版本引用、撤销和生效时间。

文档上传、索引、发布是不同状态；缺少可读原文时不能伪造比较结果。首版允许直接选取已发布文档创建事项，自动监听发布事件属于同一闭环的后续增量。

## 8. 深挖 D：经营异常复盘

“已经补过货，为什么还是断货？下次应该改什么？”

三类调查假设：需求超过当时预测、供应晚于当时承诺、决策因预算或数量限制未覆盖风险。需要同时检查这些解释，允许“多因素共同作用”和“证据不足”。

交付内容：当时可见信息、实际变化、解释的证据强弱、一个可检验的改进动作及回放结果。不能把事后更新的预测当作当时已知信息，也不能把相关关系写成因果结论。

最小版本限定三个可控原因，使用模拟器生成具有已知原因的事件轨迹。历史事实重建与规则回放比增加“评论家 Agent”更重要。若加入反事实，保持相同需求轨迹，并说明“在该模拟模型中的结果”，不称真实世界收益。

研究价值：证据隔离能否减少确认偏误；多假设并行调查是否降低错误归因；额外调用能否换来有效的后续调整。

## 9. 深挖 E：询价谈判沙盒

“分别问三家供应商，比较单价、起订量、交期和分批交货，选出适合当前目标的报价。”

每条谈判拥有独立上下文、权限和预算；中央采购 Agent 汇总报价。其他供应商的保密信息不能自动传播到各条对话。

模拟供应商必须受隐藏的底价、容量、交期和让步规则约束；LLM 只负责表达或在合法动作内选择，不能任意生成成交优惠。对手信息不能进入采购方上下文，评价器也不能泄漏隐藏底价。

除谈判成功率，还需衡量“是否找到可行方案”“同等轮数下的真实交易条件”“失败后是否选择更好的替代方案”。真实 IM/邮件发送与外部承诺需要另行接入；本轮只设计，不联系任何供应商。

它是有吸引力的独立研究题，但不能作为主闭环的必需前置。

## 10. 收敛：一个旗舰和两条扩展

推荐旗舰：**证据驱动的供应异常应对**。

推荐理由不是角色数量，而是：

- 用户从一份通知出发，能够走到一个实际采购或等待决定。
- 已有 RAG、预测、业务状态、审批、模拟器能形成完整系统。
- 同一用例既有适合简单工作流的版本，也有需要动态调查的版本，便于做公平对照。
- 时间敏感规划、证据适用性、版本失效和恢复提供了具体技术深度。
- 将来可以向多 SKU 预算规划和事件复盘演进，首版不依赖它们。

不选其他方向作为首版的理由：联合备货会同时引入全局预算和部分执行问题；谈判需要新环境；复盘缺少足够真实历史时适合研究验证但较难成为直观的首次使用入口。

这不是要把三份固定报告包装为三个 Agent。若实验说明固定流程足够，允许以工作流交付产品，同时把多 Agent 的适用边界作为研究结论。

## 11. 三种架构方案比较

| 方案 | 优点 | 局限 | 本设计定位 |
|---|---|---|---|
| 固定工作流：提取→关联→求解→解释 | 易测、开销可预测 | 难覆盖动态补查与材料缺失 | 强基线与简单路径 |
| 单 Agent＋同等工具 | 灵活、集成成本小 | 长材料和多任务上下文可能干扰，非必然 | 主对照 |
| 有界协调器＋按需专家＋确定性求解 | 隔离资料、允许独立调查与定向补查 | 调度、证据合并和失败恢复增加成本 | 候选架构 |

不采用自由互聊网络、无限递归委派、常驻“财务/审计/审批”角色。财务规则交给后端，审批由已有用户流程完成。

这与 [Anthropic 对固定工作流和动态代理的区分](https://www.anthropic.com/engineering/building-effective-agents)、[LangChain 的子 Agent 上下文隔离设计](https://github.com/langchain-ai/docs/blob/main/src/oss/langchain/multi-agent/subagents.mdx)一致；这些来源支持设计思路，不证明 ShopSteward 已有性能收益。

## 12. 可用性与研究如何同时成立

| 要求 | 本轮决定 |
|---|---|
| 可用结果 | 在一个供应异常事项中给出有证据的影响判断和可接受的行动方案 |
| 功能成功 | 目标缺口/约束正确、计划可执行、改变要求后仍能完成、成本和延迟可接受 |
| MVP 必需 | 真实 processor、时间模型、可追溯数据、有效报价、审批重算接入、最小回放 |
| 推迟的保证 | 真实商家收益证明、大规模统计、跨店扩展、谈判、生产高可用 |
| 下一步最小切片 | 一份延迟通知＋一笔已受理在途＋两个替代报价，完成影响表与可重算方案 |

功能切片可以在小场景上先跑通；大规模评测只阻塞“声称架构更优”的结论，不阻塞工程推进。

## 13. 简历与个人贡献的设计约束

可信的项目经历应覆盖一条个人负责的技术链，而非列出团队所有技术名词。

推荐个人主线：任务分解与专家工具协议→结构化证据合并→时间敏感方案工具集成→可复现对照实验。若个人还负责业务求解器和恢复机制，可以独立说明；若它们由队友实现，应明确协作边界。

完成设计只能写“设计了……”。有代码和验收后可写“实现了……”。有独立结果后才能写“相比……提升……”。没有真实经营数据，不写降低商家缺货损失或提升利润。

面试可追问的核心问题应有证据回答：

1. 为什么不使用单 Agent 或固定工作流？
2. 哪个任务由专家自主决定下一步，而不是固定调用接口？
3. 为什么总库存够仍然会断货？如何计算？
4. 不同专家看到的数据版本不一致怎么办？
5. 用户改口、进程崩溃或采购结果未知时如何继续？
6. 质量改善来自架构、更多 token，还是更好的工具？
7. 你自己实现和验证了哪些部分？

## 14. 本轮决策记录

- 已确认：课程旗舰、技术研究、可形成真实简历经历。
- 推荐并在配套设计中具体化：供应异常应对作为旗舰，文档影响作为入口，按需有界多 Agent 作为候选架构。
- 明确假设：七日、单店、单 SKU、少量供应商足以形成第一轮有意义的演示和对照。
- 暂不要求用户决定：具体模型、线上部署规模、谈判渠道、生产 SLA；使用可替换配置并在相应阶段评估。
- 后续评审最值得改动的两点：是否接受旗舰范围；个人希望重点负责运行时、求解器还是实验。它们不阻塞当前完整设计稿的形成。
