# 寻源与辅助发送

写于 2026-10-12（Asia/Shanghai），分支 `YH`。读者是要运行或演示这两项功能的人。本文说明它们做什么、怎么启用、一次演示怎么走，以及哪些已经验证、哪些没有。交付标准是概念验证：目标是在理想条件下把整条流程演示清楚。

这两项功能接在已有的“供应异常应对”（恢复 Case）和采购审批之间，连起来是一条链：

```mermaid
flowchart LR
    A[供应商资料] --> B[每家一位审查者读资料]
    B --> C[代码核对引文]
    C --> D[登记为结构化报价]
    D --> E[求解器比较]
    E --> F[解释]
    F --> G[店主采纳并批准]
    G --> H[生成订单信息]
    H --> I[店主自己发给供应商]
    I --> J[粘贴回复 生成回执]
```

几个词在本文里的意思：

- **供应商资料**：供应商发来的文本，如报价单、调价通知函、合作条款、履约记录。按门店和供应商存放。
- **审查者**：读一家供应商资料的模型调用。它只能读这一家的资料，交回一张**报价卡**。
- **报价卡**：这家供应商对所需商品的单价、起订量、装箱、交期、有效期，每一项附一段资料原文作为引文。
- **把关**：代码检查报价卡的格式和引文。引文在审查者打开过的资料里找不到，这张卡就不采用，并重读一次。
- **已对接的供应商**：报价由业务源（本项目里是模拟器）直接给出的供应商。它的报价不会被资料覆盖。
- **辅助发送**：系统不联系供应商。它生成订单信息，由店主用自己的微信或 WhatsApp 发出，再把对方的回复粘贴回来。

## 1. 寻源

### 1.1 它做什么

在一项恢复 Case 上点“开始寻源”后：

1. 系统按当前库存、需求和在途订单算出不补货时的缺口，作为对每位审查者提出的需求。
2. 每家有资料在档、且未对接的供应商各分到一位审查者，最多三位同时读。
3. 每张报价卡过把关。没过的重读一次；两次都没过的供应商不参与比较，界面上列出被退回的原因。
4. 通过的报价按单价取最便宜的三家，登记为这家门店的结构化报价。求解器一次最多比较三份报价。
5. Case 生成一个新版本，只比较刚读出的这几家，求解器给出候选和推荐。
6. 如果启用了解释，解释步骤会拿到这些报价卡，并使用离线演化产出的解释文本（默认 `sourcing-r1-s1`）。

之后的采纳、批准与原流程相同。审查者从不选择供应商或数量，这些由求解器决定。

### 1.2 启用

业务库升级到迁移头 `0019_sourcing`（在 `backend/` 下执行 `python -m alembic upgrade head`），并在 API 进程的环境里配置模型：

| 变量 | 说明 |
|---|---|
| `AGENT_API_KEY_FILE`、`AGENT_BASE_URL` | 解释所用模型服务的密钥文件和地址，与已有 Agent 共用 |
| `AGENT_CASE_MODEL`、`AGENT_CASE_API_MODE` | 解释用的模型与协议。配置了它，寻源后就会运行解释 |
| `AGENT_SOURCING_MODEL` | 读资料和读回复的模型；不设时用 `AGENT_CASE_MODEL` |
| `AGENT_SOURCING_BASE_URL`、`AGENT_SOURCING_API_KEY_FILE`、`AGENT_SOURCING_API_MODE` | 让读资料的模型走另一家服务，例如便宜的模型；不设时沿用上面的地址、密钥和 `AGENT_CASE_API_MODE` |
| `AGENT_SOURCING_ESCALATION_MODEL` | 可选，第二次阅读改用的更强模型，与读资料的模型在同一家服务 |
| `AGENT_SOURCING_REVIEW_BUNDLE` | 审查者文本版本，默认 `seed` |
| `AGENT_SOURCING_TEXT_BUNDLE` | 解释寻源方案用的文本版本，默认 `sourcing-r1-s1`；改成 `seed` 即回到演化前的文本 |
| `AGENT_MAX_OUTPUT_TOKENS`、`AGENT_MODEL_TIMEOUT_SECONDS` | 一次解释约输出 4,000 token，默认的 2048 和 30 秒不够，建议设为 16000 和 120。这两项与 Agent 共用 |
| `AGENT_CASE_EXPERTS_ENABLED` | 只决定普通的“开始分析”之后是否等待解释。寻源后的解释不看它 |

一种已经跑通的组合：读资料用 DeepSeek 的 `deepseek-flash`（`chat_completions`），解释用 OpenAI 的 `gpt-6-luna`（`responses`）。

阅读在 API 进程里后台运行，一次最长 300 秒。进程在阅读中途重启时，这次寻源会显示为中断，可以重新寻源。

### 1.3 供应商资料从哪里来

- 界面上“载入三家供应商的示例资料”会为当前商品生成三家虚构供应商的资料：安和商贸有一份已生效的调价通知，百川批发按箱报价，诚达供应链价格最低但不配送门店所在区域。这三种情况分别对应三类常见的读错。
- 接口 `POST /api/v1/stores/{store_id}/supplier-documents` 可以整体替换一家供应商的资料，每份资料是 `{doc_id, kind, text}`。界面上暂时没有逐份粘贴资料的表单。

示例资料是为演示编写的，不是真实报价。

### 1.4 接口

| 接口 | 作用 |
|---|---|
| `GET /api/v1/stores/{store_id}/supplier-documents` | 列出在档资料 |
| `POST /api/v1/stores/{store_id}/supplier-documents` | 替换一家供应商的资料 |
| `POST /api/v1/stores/{store_id}/supplier-documents/sample` | 载入示例资料 |
| `POST /api/v1/operations-cases/{case_id}/source` | 开始寻源；进度和结果在 Case 详情的 `sourcing` 字段里 |
| `GET /api/v1/text-bundles` | 列出全部文本版本、相对父版本的改动、当前用在哪一步 |

## 2. 辅助发送

### 2.1 它做什么

1. 店主批准方案后，系统核对方案仍然有效并预留资金，然后生成一段订单信息：商品、数量、单价、合计、希望送达日期和订单编号，中英文各一份。
2. 订单进入“待供应商确认”。系统不会重试，也不会轮询。
3. 店主把订单信息发给供应商，收到回复后粘贴进来。
4. 系统从回复里读出：接受还是拒绝、数量、单价、金额、送达日期、供应商自己的单号。配置了模型时由模型读，每一项必须引用回复里的原话，引不出原话的项丢弃；没有配置模型或模型失败时按固定规则读。读回复用的是读资料的那个模型（见 1.2），没有配置时用 `AGENT_MODEL`。
5. 结果有三种：
   - **确认**：回复接受订单，且提到的数量、单价、金额与订单一致。采购入账，库存记为在途；回复里给了送达日期的，预计到货改用这个日期。
   - **拒绝**：订单关闭，预留资金释放。
   - **还不能确认**：回复含糊，或数量、单价、金额与订单不一致。订单保持待确认，界面列出不一致之处，可以再粘贴新的回复。
6. 供应商一直不回复时，订单停在待确认。店主可以撤回，撤回后预留资金释放。
7. 供应商确认后，任务工作区出现“货到后在这里登记”。货到店后店主填到货件数并登记，在途转为在库，账本记一笔到货。可以分几次登记，累计不能超过订购数量。模拟器不知道这类订单，所以到货只能这样进入系统。

登记回复和撤回都需要审批权限，登记到货需要操作权限。

### 2.2 哪些订单走辅助发送

- 从供应商资料读出报价的供应商（寻源登记的），订单总是走辅助发送，因为没有可以直接下单的系统。
- 其余订单由 `PURCHASE_CHANNEL` 决定：默认 `simulator`，即原来的直接提交；设为 `assisted` 后全部走辅助发送。
- 审批接口 `POST /api/v1/plans/{plan_id}/decision` 的请求体可以带 `channel` 指定单笔订单的方式。

### 2.3 接口

| 接口 | 作用 |
|---|---|
| `GET /api/v1/actions/{action_id}` | 订单状态，含 `channel`、`order_message`、`supplier_reply` |
| `POST /api/v1/actions/{action_id}/supplier-reply` | 登记粘贴的回复，请求体 `{text}` |
| `POST /api/v1/actions/{action_id}/withdrawal` | 撤回未确认的订单 |
| `POST /api/v1/actions/{action_id}/arrival` | 登记到货，请求体 `{quantity}`；不带数量表示未到的全部到齐 |

## 3. 一次演示怎么走

前提：业务 API、业务 worker 和前端在运行，模型已按 1.2 配置，当前店铺有一项进行中的备货委托，且原订单晚到造成了缺口。

1. 在任务工作区展开“供应异常应对”，填预算，点“开始分析”。
2. 在“寻源”一栏点“载入三家供应商的示例资料”，可以展开查看原文。
3. 点“开始寻源”。三张报价卡陆续出现：安和商贸的单价来自调价通知而不是报价单；百川批发的单价由每箱价格换算；诚达供应链因不配送而没有报价。展开“每一项的出处”能看到引文。
4. 候选列表更新为这几家，带推荐；“专家分析”里是解释。
5. 点“生成待确认方案”，在方案卡里核对并确认。
6. 出现“把这份订单发给供应商”卡片。点“复制订单信息”。
7. 在回复框粘贴一段供应商回复，例如“收到，20件没问题，单价8.60元，10月15日送到”，点“登记回复”。
8. 订单变为“供应商已确认”，采购与到货记录里能看到回执和每一项的原话。
9. 出现“货到后在这里登记”卡片。点“登记到货”，在库数量增加，在途归零。

想展示“还不能确认”，可以先粘贴“可以，但只有10件”。

回复里的数量和单价要与这一轮的订单一致，订单才会被确认。示例资料的价格随当前商品生成，每轮可能不同，照着订单卡片上的数字写回复。

第 1 步之前需要一家店和一项进行中的备货委托；没有可用的日预测时，在“补充七日需求情景”里填七天的需求和首日结算时间。

“学习与经验”页底部的“提示词版本与自进化”列出每个文本版本、它相对父版本改了什么、现在用在哪一步。

真实模型冒烟在示例资料上跑了两次，每次是一轮完整的寻源加一次回复解读：

| 读资料 | 解释 | 耗时 | 三家是否读对 | 推荐 | 解释 |
|---|---|---|---|---|---|
| `deepseek-flash` | `deepseek-flash` | 约 84 秒 | 是，都是第一次阅读就通过把关 | 百川批发 20 件 | “部分完成”，二十多条 |
| `deepseek-flash` | `gpt-6-luna` | 约 61 秒 | 是，都是第一次阅读就通过把关 | 百川批发 20 件 | “部分完成”，15 条 |

- “读对”指：安和商贸读出 9.20 元（调价通知的价格），百川批发读出 8.60 元（每箱 86.00 元换算），诚达供应链判为门店不在配送范围。
- 解释用的是 `sourcing-r1-s1`。两次的状态都是“部分完成”，原因是模型列出了它认为缺少的资料。解释是英文的，逐条照抄求解器的字段。
- 第二次的用量：三位审查者合计输入约 10,800、输出约 4,800 token；解释输入约 6,300、输出约 4,000 token。
- 回复“好嘞老板，20件没问题，还是八块六一件，周四给你送过去”两次都由 `deepseek-flash` 读出：接受，20 件，8.60 元，送达日期按业务日期推到周四，每项都带原话。

两次运行说明这条路能走通，不说明它每次都读对。重跑的方法：设置环境变量 `SOURCING_LIVE_KEY_FILE` 为读资料模型的密钥文件路径，可选 `SOURCING_LIVE_MODEL`、`SOURCING_LIVE_BASE_URL`、`SOURCING_LIVE_API_MODE`；要让解释走另一家服务，再设 `SOURCING_LIVE_CASE_KEY_FILE`、`SOURCING_LIVE_CASE_MODEL`、`SOURCING_LIVE_CASE_BASE_URL`、`SOURCING_LIVE_CASE_API_MODE`。然后带 `-s` 运行这一项测试。

## 5. 已知的限制

- 一次寻源只把最便宜的三份报价交给求解器，其余读出的报价会列出但不参与比较。
- 寻源只比较从资料读出的供应商，不把原来已对接的供应商放进同一次比较。
- 辅助发送的订单到货要由店主登记。模拟器不知道这笔订单，不会产生到货事件；店主不登记，库存就一直停在在途。
- 规则读法只认常见写法，如“40件”“单价10元”“10月15日”。口语化的回复需要配置模型才能读出。
- 回复里同时出现接受和拒绝的字眼时，规则读法按“还不能确认”处理，留给店主判断。
- 寻源方案的解释是英文的，条目多。演示时如果嫌长，可以把 `AGENT_SOURCING_TEXT_BUNDLE` 改回 `seed` 对比，或者只展示候选和推荐。
- 方案生成后默认 15 分钟过期（`PLAN_TTL_SECONDS`），寻源结束后要在这段时间内采纳并批准。订单发出后等待供应商回复不受这个时限约束。
