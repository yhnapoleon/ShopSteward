## 真实执行与三例B1失败

- dev-pt07-011，decision：负数-8被变成+8并试算；应询问合法数量。
- dev-pt07-014，decision：最低量30被handoff；固定金标为clarify以确认是否接受上限语义。转交没有错误写入，但不符合本轮路由契约。
- dev-pt04-019，execution：23 units已在数据约定中表示23件，模型仍再次澄清，没有执行工具。同例decision模式通过；两种模式重新调用，不能假定温度0在不同对象ID/前文问题下总是相同。

B0核心执行7次错选写动作，其中4次实际修改测试方案（PT01-016/017、PT03-019/020），3次被EXPLICIT_REVISION_REQUIRED拒绝（PT01-019/020/035）。这些拒绝均阻止了错误动作，没有“语义正确却被后端拒绝”的实测案例。backend_policy_mismatch是按错误码命名的原始标签，不能据此断言后端规则应该放松。此次不修后端规则。

## 错误解释与Data下一步

[42条解释（40个不同案例）](failure-analysis.md)覆盖全部主要错误类型，已全量检查B0/B1失败，不将跨模式重复视为独立证据。优先建议：

1. **补数据：数字语义与意图对照。**成对覆盖-8/8、负三/三、0/null、旧值/新值、否定/纠正/转述、试算/正式修改；保留符号，不由后处理静默修正。B1真实负号错误使该项优先级最高。
2. **补数据：相对运算与历史引用。**当前值+增量、减半/翻倍、首个/最后一个/两个相同值，与数量缺失严格区分。B0此类失败明显；B1本集通过，后续用基础模型确认是否需要较高训练配额，不因为规则差就盲目扩写。
3. **修上下文/协议并补数据：单位与一次澄清。**明确件/units是否为等价别名，包装必须换算；明确收到足够回复后立即执行。覆盖“缺数量但旧上限已知”与“新数量已给”配对。B1重复澄清来自这一边界；先固定契约，再制作新训练样本。
4. **补数据并固定路由定义：上限、下限、精确量和范围外请求。**最低/精确量统一选择澄清或转交的产品约定，当前Eval保持clarify金标；训练中避免把两条冲突路线同时标正确。增加撤回当前请求但保留任务的短句。
5. **后端规则限制单列：**4次错误修订被接受、3次被拒绝说明关键词并不完整表达用户意图。作为以后接入产品的已知限制登记，不能通过放松网关让Eval分数上升；本阶段不扩建生产防护。

上述建议面向新来源/新场景训练数据，不把dev金标或其同模板改写直接导出为训练集。B2未测、SFT未训练，本报告是评测能力与现有策略基线，不能证明微调收益。
